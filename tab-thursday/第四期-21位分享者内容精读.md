# 第一部分 · 工具、上下文与验证

## 01 海涛：Ulysses、Pinky 与自建服务

**身份**：常驻上海的投资分析师，个人主页写明关注 AI 软件、AI 基础设施与生成式模型，日常也自己写代码做工具（haitao.wiki）。这是他第四次在 Tab 星期四分享，前三次的题材集中在设备、Agent 与日常工具（官方汇总页记录）。
**分享对象**：一组他自己在用的工具，覆盖长文写作、在 Mac 上运行 Windows 游戏、用 Agent 操控手机，以及两个长期自建的服务。
**关键词**：长文写作、手机自动化、MCP、API 网关。

### 他讲了什么

**写作。** Ulysses 定价页写明 5.99 美元/月或 39.99 美元/年，含 Mac、iPad、iPhone 三端与 iCloud 同步（ulysses.app）。官网首屏列出的能力包括 Apple Design Award、20 多种语言的语法与风格检查、把稿子转成 PDF、Word 与电子书，以及发布到 WordPress、Ghost、Medium 和 Micro.blog（ulysses.app）。官方汇总页记录它用 Markdown XL 支持批注、脚注与文稿片段拼接。Setapp 收录的说明来自官方汇总页记录；本次只确认 setapp.com/apps/ulysses 页面存在，正文由脚本渲染，未能读到订阅权益的具体条款。

**游戏。** 他在 Mac 上通过 CrossOver 加苹果 D3DMetal 转译层运行了《黑神话：悟空》（官方汇总页记录）。这类组合的做法是把 Windows 游戏的图形调用翻译成 Metal，再交给苹果的 GPU 驱动执行【推断】。官方汇总页没有给出机型、画质与帧率，公开材料也没能核验实际表现。

**手机自动化。** 手机端他推荐 DIYgod 开源的 Pinky。仓库用 Go 编写，Apache-2.0 许可，2026 年 11 月 6 日创建，到 11 月 25 日有 2,779 个星标、292 个 fork（api.github.com）。README 自己标注的是 pre-alpha 阶段，并写明不用 Electron：窗口由 MyGo 在 GPU 上绘制，安装包 16 到 22 MB，在 Mac 上空闲时约 70 MB 内存、0% CPU（github.com）。支持范围是 Android 10 到 17、iOS 17.4 及以上，iOS 27 及以上手机端不用安装任何东西；Agent 通过 MCP 接入，可以是本机的 Claude Code、Claude Desktop、Codex、Cursor，也可以走 HTTP。

**审批与隔离。** 付款、交易、转账这类按钮默认等待用户点击，规则写在 Pinky 的网关里，README 写明审批由网关执行，Agent 的指令无法替自己放行；银行、钱包、密码器类 App 对 Agent 不可见，密码与一次性验证码输入框不能键入，按钮识别覆盖 10 种语言（github.com）。官方汇总页记录的 60 帧投屏与拔线 5 秒内热切 Wi-Fi，README 只写到拔线后程序自动切到 Wi-Fi、期间调用等待几秒，没有给出帧率与切换秒数。

**两个自建服务。** CLIProxyAPI 是 MIT 许可的 Go 项目，2025 年 7 月 1 日创建，59,442 个星标、9,131 个 fork；它把 Antigravity、ChatGPT Codex、Claude Code、Grok Build、Muse Code、Devin 这些 CLI 订阅，包装成 OpenAI、Gemini、Claude、Codex 兼容的接口（github.com），管理面板另有一个仓库。闲鱼监控用 ai-goofish-monitor，MIT 许可，Python 编写，20,806 个星标；它用 Playwright 抓取页面，按自然语言生成判断标准，再用多模态模型审图与文案，结果通过 ntfy.sh、企业微信、Bark、Telegram 或 Webhook 推送，支持账号与代理轮换，默认 Web 界面在 127.0.0.1:8000（github.com）。这两个项目都出自他人之手，他做的是部署与长期使用。

### 关键点分析

**第一，写作工具的长期价值在发布与导出通道。** Ulysses 能把稿子推到 WordPress、Ghost、Medium、Micro.blog，也能转成 PDF、Word 与电子书（ulysses.app）。这条能力决定了文字能不能离开编辑器。换工具时的实际成本，往往在旧稿的格式与图片引用要不要重新排一遍。导出的文件同时是一份可以长期保存的备份。挑写作软件先测出口，比先看界面省事。

**第二，手机自动化的关键设计是把审批放进网关。** Pinky 的 README 写明审批由网关执行，Agent 无法替自己放行；银行、钱包、密码器默认不可见，验证码输入框不能键入（github.com）。这层设计意味着即使屏幕上的文字诱导 Agent，规则仍然生效。做同类工具时，把危险动作的判断写进无法绕过的执行层，比在系统提示里反复叮嘱可靠。

**第三，MCP 把手机变成任何客户端都能调用的设备。** Pinky 提供 MCP 服务，Claude Code、Claude Desktop、Codex、Cursor 与自写脚本都能连接（github.com）。设备能力一旦以协议暴露，用户就不必绑定某一个 Agent。一台手机同时接多个客户端时，冲突处理成了新的问题。随之而来的是授权：每个新 Agent 第一次连接都要单独批准，权限范围由人指定，这一步很容易被随手点过。

**第四，把订阅转成标准接口是一次成本结构的调整。** CLIProxyAPI 让已有的 CLI 订阅能被任何兼容 OpenAI 接口的客户端调用（github.com）。省下的是重复购买额度的钱，付出的是稳定性与账号风险：上游一旦改动鉴权或限流，本地网关需要跟着改。这类项目迭代很快，59,442 个星标背后是大量使用者同时盯着兼容性。

**第五，信息筛选的成本被转移到了模型调用。** 闲鱼监控的流程是抓页面、生成判断标准、用多模态模型审图与文案，再把通过的商品推送出去（github.com）。真正的工作量在判断标准这一段：标准宽，无关商品会一起送来；标准窄，合适的东西会被漏掉。20,806 个星标说明这件事的需求很普遍，也说明写好标准比跑起程序难。

**第六，跨平台转译层是 Mac 上运行 Windows 游戏目前的主要路径。** CrossOver 加 D3DMetal 的组合由官方汇总页记录，本次没有拿到可核验的帧率与画质数据。这类方案的效果取决于具体游戏用到了哪些图形特性【推断】。用它之前，先查这款游戏在转译层下的实测记录，比直接购买更省时间。

### 可迁移的方法

1. 挑写作软件先测导出：拿一篇带图、带脚注的旧稿，分别导出 Markdown 与 PDF，看格式有没有丢。
2. 给 Agent 的手机操作划三条底线：支付类按钮必须人工点击，密码与验证码输入框不接受键入，新 Agent 首次连接单独授权。
3. 把已有订阅接进兼容接口前，先记下上游的鉴权方式与额度规则，改动后当天重测一遍。
4. 做信息筛选类工具，先把「什么算符合」写成一页可以复用的判断标准，再交给模型执行。
5. 长期运行的自建服务用容器部署，把数据目录挂出来，升级时只替换镜像。

### 边界与提醒

Pinky 的 README 标注 pre-alpha，多个功能「还没有人试过」，官方汇总页给出的 60 帧与 5 秒切换在仓库里找不到对应数字。把日常手机交给一个 pre-alpha 项目，代价是账号风险与不稳定的连接，iPhone 端还需要开发者磁盘映像与 Xcode 环境。

用 CLIProxyAPI 把订阅开放给其他客户端，是否越过订阅条款需要使用者自己判断，账号被限制的风险由使用者承担。闲鱼监控依赖登录态抓取页面，平台规则改动会让整条链路失效。

## 02 杨云童：Handoff、ManuFold 与上下文的托管

**身份**：独立开发者，个人站点的关于页写明她是北京大学软件与微电子学院 2026 届硕士，做过 Kimi 与飞书的 AI 产品，现在全职做自己的工具（yytyyf.com）。页面列出的产品有十七件，多数已上线或在内测。
**分享对象**：把个人上下文安全交给 Agent 的一组工具：Handoff、物页 ManuFold 与 KeyKeeper。
**关键词**：上下文托管、结构化提示词、本地文件、密钥注入。

### 她讲了什么

**Handoff。** 官网的定位是「存链接和一句话，Agent 把它们变成派单」。手机端用系统分享存链接、截图、语音，Mac 端的管线读那句原话与截图内容，判断属于哪个项目，生成一段可以直接粘给 Agent 的提示词（handoff.yytyyf.com）。提示词按固定骨架写：任务、背景原话、相关链接、项目位置、产物要求、完成后回写结果，六节齐全，换一个全新的会话也能开工。数据是文件夹里的 Markdown，一条笔记一个文件，没有数据库，也不经过服务器；管线只存用户给的东西，不抓网页正文，不伪装浏览器。

**ManuFold。** 物页解决说明书塞满抽屉的问题：拍下说明书，纸质版可以处理掉，需要时直接问，AI 按你拍的那一本回答，每一步标出页码，点开能对照原图（manufold.yytyyf.com）。官网写明文字识别在手机上完成，提问与摘要只把识别出的文字和问题发到云端，通过硅基流动调用 AI，照片不上传，服务器不保存提问与说明书内容。目前是 iPhone 内测，照片默认存在本地，可以打开 iCloud 同步。

**KeyKeeper。** 官网的诉求是让 Agent 管密钥，又看不到密钥的值。当前版本 v0.3.7，免费，Apple Silicon，要求 macOS 14 及以上，不用注册账号（keykeeper.dev）。密钥存在 macOS 钥匙串，Agent 调用时弹窗说明用途与授权时长，四个选项分别是拒绝、仅这一次、本次运行期间、以后不再询问；批准之后密钥通过 `keykeeper run` 注入子进程的环境变量，进程结束即消失；保存密钥时会用一次只读请求向服务方确认是否可用。内置 98 家服务商的接入模板，写明密钥在哪申请、该勾哪些权限、真钥匙长什么样、怎么验证。

**另外两件。** Swob 用来复盘历史编程会话，官网写明它读取 Claude Code、Codex、Cursor、OpenCode 留在本机的会话，整理成可搜索的库，并给出一个具体背景：Claude Code 默认在 30 天后清理历史（swob.app）。版本 v1.3.1，Apache-2.0，仅 Apple Silicon。还有一件是她让 Grok Bot 每天读一次本地解密的微信记录，追踪自己与他人的关系变化（官方汇总页记录）；Grok Bot 的产品页由脚本渲染，本次未能读到正文。

### 关键点分析

**第一，Handoff 的判断是把「收藏」改造成「派单」。** 官网把问题写得很直白：收藏夹是想法的坟场。改动之后，存下来那一下要顺手写一句「对哪个项目有用」，这句话成了归类依据，项目不必是文件夹，「减肥」也算一个项目。一条链接配上意图，才具备交给 Agent 的条件；没有意图的链接留在原处，不会凭空生成待办。

**第二，提示词的骨架比措辞重要。** Handoff 的六节结构把 Agent 开工所需的条件固定下来：做什么、依据什么、原话是什么、代码在哪、要交什么、怎么回写。任何一节缺失，换个新会话就要人来补。骨架稳定之后，换模型不用重写提示词。这套骨架换到别的工具里同样成立。

**第三，数据的形状决定了可迁移性。** 一条笔记一个 Markdown 文件，没有数据库，没有私有格式，可以放进 Obsidian 或者 Git（handoff.yytyyf.com）。文件本身是接口，任何 Agent 读到这个文件夹就能看懂状态。出口是剪贴板，今天给 Claude Code，明天给别的工具，派单的一方不需要知道对面是谁。代价是没有检索与统计能力。

**第四，密钥管理的分界线在值有没有进入模型上下文。** KeyKeeper 把密钥锁在钥匙串，运行时才注入子进程（keykeeper.dev）。Agent 可以发起调用、看到调用成功，却读不到那串字符。审批给到四个时长选项，把「一次」和「永久」分开，比只有一个允许按钮更接近真实使用。98 家模板覆盖常见服务商，剩下的要自己填字段，这一点决定了它在团队里的推广成本。

**第五，说明书场景的难点是不许自由发挥。** ManuFold 的回答限定在你拍下的那一本，每一步标页码，点开能对照原图（manufold.yytyyf.com）。这个约束牺牲了覆盖面：说明书里没写的问题，它不会替你猜。文字识别在本地完成、只上传识别出的文字，是把隐私成本压到可接受范围的做法，代价是识别质量受手机端模型限制。

**第六，复盘类工具补的是上下文的所有权。** Swob 读取本机会话，把散在各自工具里的记录合成一个可以搜索的库，官网页面上写着 Claude Code 默认 30 天清理历史（swob.app）。会话一旦过期，经验的连续性就断了。把记录导出成自己的文件，等于给长期使用 Agent 留一份底稿，这件事在换工具、换机器的时候价值最高。

### 可迁移的方法

1. 存链接时顺手写一句「对哪个项目有用」，这句话就是后来的归类依据。
2. 给 Agent 的待办写成六节：任务、背景原话、相关链接、项目位置、产物要求、完成后回写命令。
3. 个人资料存成纯文本加附件，一条一个文件，随时可以整个拷走。
4. 密钥只放进系统钥匙串，用命令行注入子进程，用完即失效。
5. 让 AI 读文档类材料时，要求每条结论标注来源页码，并保留原图入口。
6. 每隔一段时间把 Agent 会话导出来复盘，先看自己改了几次方向。

### 边界与提醒

Handoff 与 ManuFold 都标着内测，官网的「申请内测」「加入 waitlist」说明入口还没有完全开放，两件产品的稳定性没有公开数据。Handoff 不抓正文，代价是它不知道链接里写了什么，归类全靠用户那句原话与截图内容。

KeyKeeper 只做 macOS，Windows 与 Linux 用户用不上；98 家模板之外的服务需要自己填。把密钥交给一个第三方程序保管，前提是信任它的代码与更新渠道，公开仓库这次只核对到 Swift 源码与许可证文件，GitHub 未识别出标准许可证标识（api.github.com）。

用 Grok Bot 读微信记录这一件，只有官方汇总页的文字记录，公开页面读不到她的讲述。这类做法涉及他人数据，官方描述里没有提到征得对方同意的方式，读者不宜直接照搬。

## 03 yikai：ARTEX 与自主渗透的两面

**身份**：官方汇总页只给了他的即刻主页链接，公开访问读不到正文，本次未能核验他的职业与背景。按官方记录，他没有网络安全经验，用 ARTEX 接廉价模型检查 AI 极速开发的产品接口（官方汇总页记录）。
**分享对象**：开源的多智能体自主渗透系统 ARTEX，以及绕开模型拒答的三条路。
**关键词**：多智能体、双图架构、资产图、模型拒答。

### 他讲了什么

**系统是什么。** 官方汇总页记录：输入一句目标之后，Planner 在资产图与探索图上循环理解意图，指挥多个 Worker 调用安全工具链持续找漏洞。现在的仓库写明它 fork 自 Autumn-27/ARTEX，保留上游提交历史与 AGPL-3.0 许可，由 ChainReactors 持续维护（github.com）。上游仓库地址现在返回 404，官方汇总页记录的原因是这个工具被黑客用来攻击多国金融机构，原作者关闭仓库并删除了代码。

**架构。** 后端是 Go 单体，内嵌 Next.js 前端，数据库用 PostgreSQL，默认端口 8787；Agent 能力由 norma SDK 提供（github.com）。核心是两张图。资产图跨任务共享，节点包括主域、子域、IP、服务、应用、端点，并归属到公司，父子关系与去重键由程序计算，Agent 只提交原始信息。探索图每个任务一份，节点分目标、意图、事实、漏洞、提示，靠派生关系连成链路，回答某个方向从哪里来、产出了什么。README 写的分工是：planner 读探索图态势，只在存在未覆盖方向时把意图派进前沿；worker 领一条意图，用真实工具执行，把新资产、事实与漏洞写回两张图，然后停下。

**规模与限制。** 仓库 2026 年 10 月 9 日创建，2,597 个星标、1,560 个 fork，AGPL-3.0（api.github.com）。README 开头写明：严禁将本工具用于任何实际的渗透测试、攻防对抗或生产环境。在线 Demo 只跑前端，构建时打开模拟开关，用假数据展示界面，不执行真实扫描。

**成本。** 官方汇总页记录，他接上廉价模型，花 5 到 15 元就能把一套接口的权限问题试出来。这类 AI 极速开发的产品常见两种情况：第三方 SDK 凭据被打进安装包，或者留下没有鉴权的接口。这笔金额属于现场记录，没有公开账单可以核对。

**绕过拒答。** 官方汇总页列了三条路：零数据留存的无审查推理平台 Yeta Labs、Codex 指令集 gpt-instruct、开源权重修改工具 heretic。Yeta Labs 首页写明提供无审查的开放模型接口，并承诺提示与输出不被保存（yeta.ai）。heretic 的运行方式不需要训练，默认动作就是压制拒答，用 Optuna 搜索参数，评分同时看拒答率与 KL 散度；README 举例，RTX 3090 上用默认配置处理 Qwen3-4B-Instruct-2507 约 30 到 40 分钟（github.com）。gpt-instruct 是面向 Codex 的提示词与测试包，MIT 许可，按 gpt-6.1-sol、gpt-6-astra、gpt-5.6-sol 三条分支维护（github.com）。

### 关键点分析

**第一，ARTEX 的工程重心在让多 Agent 不重复劳动。** 资产图是跨任务共享的事实库，探索图记录每个任务的推进链路，两个 worker 之间的观察靠过程级的活动记录流动（github.com）。多智能体系统最常见的问题是几个 Agent 反复试同一个方向，或者一个已经得到的结论没有传给下一个。把共享事实与单次推进分开存放，才让并行有意义。

**第二，planner 与 worker 的边界决定了任务能跑多久。** planner 只负责派意图，worker 领一条、做完、写回、停下，这个约束把循环的终止条件写在了角色定义里（github.com）。没有这层约束，Agent 容易在没有新方向时继续空转，成本随时间往上加。把「什么时候不再派活」写清楚，比优化每一步的工具调用更能控制开销。

**第三，资产图的结构由程序计算，Agent 只交原始信息。** README 明确层级与去重键由程序完成，Agent 提交原始信息（github.com）。这条分工针对的是模型编造层级的倾向：让它判断某个子域属于谁，迟早会出现凭空的归属关系。把可计算的交给代码，把观察交给模型，这个划分对任何长期运行的智能体系统都适用。

**第四，成本下降重新写了攻防两侧的时间表。** 5 到 15 元跑完一套接口的检查，意味着验证一个漏洞假设的代价低到可以反复试（官方汇总页记录）。防守方要面对的是窗口缩短：CVE 公布之后，差分逆向与批量试探可以由 Agent 完成。Chris Pang 在同一场分享里引用的 GTIG 报告说的就是这件事（官方汇总页记录）。

**第五，绕开拒答的三条路，代价分别出现在不同地方。** 换平台把风险交给服务方的合规状况；改提示词依赖模型的版本，一次更新就可能失效；改权重需要一张能跑起来的显卡与一次几十分钟的运行（github.com）。三条路的共同前提是使用者已经知道自己要做什么，工具本身不解决这个问题。

**第六，这类工具的两面同时写在仓库第一屏。** README 开头就禁止实际渗透使用，而同一份仓库又如实记录了上游被用于真实攻击、原作者删库的经过（github.com）。开源一套攻击能力，作者无法选择使用者。把禁用条款写在第一屏，是作者在发布之后能做的少数几件事之一，其余的交由使用者判断。

### 可迁移的方法

1. 把共享事实与单次推进分成两张图：一张全局、一张按任务。
2. 给多智能体系统定明确的停止条件：领一条意图、执行完、写回、立刻结束。
3. 让程序计算层级与去重，让模型只提交原始观察，两边职责写进文档。
4. 每次运行前设三项预算：模型调用次数、时间上限、金额上限。
5. 在仓库第一屏写清使用范围与禁止事项，降低被误用的概率。

### 边界与提醒

ARTEX 的 README 禁止实际渗透使用，官方汇总页又记录了它在真实攻击中被使用、原作者删库的经过。两件事放在一起说明：一套开源工具一旦发布，作者能控制的只剩许可证与文档。

他的身份与现场数据都只有官方记录支撑。即刻主页由客户端渲染，读不到正文；官方链接到的那篇防守方分析文章在访问时返回环境异常验证页，本次未能读到内容，因此关于流量特征与封禁手法的部分无法核验。

heretic 这类免训练修改在降低拒答率的同时会改变模型的其他行为，README 自己列了减少套话、减少奉承、改变情绪倾向等多个配置（github.com）。改完的模型需要重新跑一遍评测。

## 04 Aria：《精益创业》的重读与证伪

**身份**：官方汇总页给出的主页是 nekoium.com，站点以 Crescent 为名，写明他在做的是「AI 时代人的成长基础设施」，五个进行中的项目分别覆盖知识摄入、知识组织、技能训练、注意力与知识内化（nekoium.com）。联系页列出英语 IELTS 7.5、日语 N1、德语 TDN3，并写明他运营一个叫 Qxeer Jam! 的线下交流活动（nekoium.com）。
**分享对象**：脱稿重读 Eric Ries 2011 年出版的《精益创业》，以及他对「AI 时代最小可行产品是否还有用」的回答。
**关键词**：最小可行产品、证伪、验证性学习、成长基础设施。

### 他讲了什么

**重读的理由。** 分享里引到两句书中的原话：「一切能想象到的东西现在都能开发出来」「大家害怕产品被极速抄袭」。这两句写于 15 年前，放进 2026 年的 AI 浪潮里仍然成立（官方汇总页记录）。这次分享是脱稿，没有公开的幻灯片可以对照。

**MVP 的用途。** 面对「AI 抄一个 MVP 太快，MVP 还管不管用」的质疑，他的回答是：MVP 的作用有且仅有一个，就是收集信息（官方汇总页记录）。哪怕 0 人使用，也是一次高价值的证伪，能省下盲目开发两年的成本（现场记录）。

**Crescent 的五个项目。** 站点把「成长基础设施」分成五件：SRS + CI 把间隔重复与可理解输入组合起来做语言学习；Flexity 用多轴的知识记录框架替代只有状态一列的看板；Icarus 把公开的绘画训练方法整理成可复现的练习；另两件分别针对无意识使用手机的行为设计与知识的内化管道（nekoium.com）。页面上这些项目都标着进行中。

**跨界学习的预算。** 他的主张是主业深耕，跨界领域借《The First 20 Hours》的方法学到 60 分，够与专家对话即可（官方汇总页记录）。

**Olea。** 他开源的安卓本地 Agent 编排器基于 Ubuntu Base 与 Termux PRoot，免 root、免电脑中继，在手机本地跑 Pi、Codex 与 Claude Code，并可通过无障碍服务受控操作手机（官方汇总页记录）。仓库为 MIT 许可，当前版本 0.1.1，只发 ARM64 的 Android 包，README 写明设备兼容与持续后台执行尚未验证（github.com）。

### 关键点分析

**第一，判据换了位置。** 讨论 MVP 最常见的争论是它够不够完整、能不能吸引用户。他把判据挪到「这次运行要回答什么问题」，产品形态退到次要位置（官方汇总页记录）。一个够难看的页面只要能把假设测出来就完成了任务；做得漂亮却读不出结论的页面什么也没完成。

**第二，证伪可以计价。** 他说 0 人使用能省下两年（现场记录）。这句话的价值在于把失败换算成成本：两年投入换一次明确的信息，交易划算。先算清假设错了会损失什么，再决定 MVP 做多完整，比抽象讨论「最小」更实际。

**第三，抄袭变快改变的是时间窗口。** AI 让一个界面几天内被复制，第一个做出来的领先时间被压缩（官方汇总页记录）。MVP 要拿的信息仍然只有真实用户能给，复制你的人不会替你验证需求。窗口变窄之后，每次验证能提取多少可用结论成了关键。

**第四，重读的价值在检验结论的适用条件。** 2011 年的书讨论的是当时的开发成本与渠道。工具把开发成本压低之后，书里关于小批量、快速迭代的论证仍然成立，先做出来再改的门槛变了【推断】。把结论与它依赖的条件分开看，比记住结论有用。

**第五，五个项目共用一套反馈设计。** Icarus 的出发点是：打音游几小时能感到进步，练乐器同样的时间却感觉不到，差别在反馈是否可见（nekoium.com）。这条观察被他推广到语言学习与知识管理：让人看见自己在变好，练习才持续得下去。

**第六，Olea 把主张变成可安装的东西。** 端侧 Agent 常见做法是手机当遥控器，算力放在电脑或服务器。Olea 去掉中继，让 Agent 与工作文件都留在手机上（github.com）。代价写在 README 里：兼容性与后台执行都没有验证，模型请求仍然要联网。

### 可迁移的方法

1. 每个 MVP 开工前写一句：这次要回答哪个问题，什么结果算否定。
2. 把最坏情况下的损失换算成金额与时间，用它决定投入上限。
3. 拿到 0 用户的结果时，先确认渠道有没有触达目标用户，再判定假设。
4. 跨界学习设 20 小时的封顶预算，目标是能听懂专家的话并提问。
5. 一套长期主张分成三到五个能被别人试用的项目，每个留公开入口。

### 边界与提醒

「省下两年」「0 人使用」都是现场口述（官方汇总页记录），没有对应的项目数据可以核对。他给的是判断方法，没有可以复现的实验记录。

《精益创业》的方法在学界有明确批评：沃顿商学院的 Ethan Mollick 认可它对实验与学习的强调，同时指出在新技术场景下过早依赖早期用户输入会出问题（en.wikipedia.org）。做没人见过的产品时，用户的反馈本身可能失真。

Olea 的 README 写明 Pi 的文件操作、中断与会话续接在 Android 14 的 ARM64 机器上验证过，其余组合没有同等覆盖，也没有 iOS 版本（github.com）。把它当日常工具之前，先确认自己机型有没有实测记录。

## 05 Yorkson：开源掌机与跨平台移植生态

**身份**：博客 blog.yorks0n.com 从 2022 年起持续更新，文章集中在文献追踪、单细胞分析、植物基因组数据可视化与 Rust 小工具，也写数码产品与游戏（blog.yorks0n.com）。关于页写明 Yorkson 是高中时起用的英文名，来源一部早年国漫，少数派上也发过文章（blog.yorks0n.com）。他在第二期讲 ZotWatch、第三期讲 Pebble，这一期换了掌机（本文档前面的重复分享者表）。
**分享对象**：从百元级 Linux 小掌机到 Steam Deck 的一条设备谱系，以及把 PC 与主机游戏搬上这些设备的几条路径。
**关键词**：原生移植、转译层、双系统、兼容率。

### 他讲了什么

**百元级 Linux 掌机。** 这类机器的长处是秒开即玩，游戏由社区做原生移植，不经模拟器。PortMaster 首页写明收录 1,500 多款游戏、支持 40 多款 Linux 掌机、累计下载 10,065,479 次、199 位移植者、当月新增 51 款（portmaster.games）。支持设备页列出的 40 款机器多数是 640×480 屏幕、1 GB 内存，芯片为 RK3326 与 H700 一类低功耗方案（portmaster.games）。他点名的《星露谷物语》《蔚蓝》《小丑牌》都在这个库里（官方汇总页记录）。

**两三千元的骁龙安卓掌机。** 这一档今年在软件转译上集中爆发。刷机双系统方案 Zaviya 基于 SteamOS 的 ARM 版本，GPL-2.0 许可，v1.5 起每个芯片一个 `.img.zst` 镜像，可写入 microSD 卡或装进内置存储与 Android 并存，开机由 OpenABL 菜单选择；x86 游戏经 FEX 加 ARM64 版 Proton 运行，桌面是 KDE Plasma，双屏机型能把底部屏当启动器、游戏工具与触控板（github.com）。

**免刷机的两条路。** DroidDeck 把 Steam 的 Gaming Mode 直接搬到 Android，0.7.1 版 2026 年 11 月 10 日发布，APK 92 MB，要求 Android 9 及以上，GPL-3.0，页面记录下载 1,877,613 次、116 位贡献者，推荐 Adreno 730 及以上的 GPU；Android 14 及以上要在开发者选项里关掉子进程限制，不需要 root；需要内核级反作弊的游戏多数不能联机（droid-deck.dev）。小鸡的盖世游戏免费提供 PC 模拟器、云游戏与串流，接入 Steam 与 EPIC 两个库（gamehub.xiaoji.com）。

**双屏与高端。** 国产双屏安卓掌机为《星露谷物语》做了上下屏联动（官方汇总页记录）。再往上是 Steam Deck 与 ROG 掌机。中场休息时他带去的实体机被大家轮流上手，成了现场说的「赛博核桃」（现场记录）。

**iOS 一侧。** 苹果不允许运行时生成可执行代码，App Store 里的 Delta 支持到 NDS，页面列出 NES、SNES、N64、Game Boy 系列、NDS 与 Sega Genesis（apps.apple.com）；Manic EMU 的页面列出 3DS、GameCube、Wii、PSP、Dreamcast 等更多机型（apps.apple.com）。更激进的路线是 S2Arm：把同为 ARM64 的 Switch 游戏代码静态重写为苹果原生指令，图形调用走 Metal，0.6.0 起手机上只装一个 App，游戏由 Mac 或 Windows 启动器逐个推送；运行设备要求 A14 或 M1 及以上芯片、iOS 18 及以上，出包的 Mac 要求 Apple 芯片与 macOS 15 及以上（s2arm.com）。正版案例是心动网络收购 IP 后推出的《火炬之光 II》全苹果生态原生移植，TestFlight 页面写明覆盖 iPhone、iPad、Mac、Apple TV、Apple Vision Pro，支持 iCloud 存档同步，当前显示名额已满（testflight.apple.com）。

**他的实测。** 中端安卓掌机跑中小型独立游戏，兼容率八九成；3A 大作仍然看运气（现场记录）。

### 关键点分析

**第一，Linux 掌机赢在启动时间。** 秒开即玩意味着没有兼容层初始化、没有着色器编译、没有登录。这条体验上的差别来自游戏本身是原生移植的，与设备的性能关系不大（portmaster.games）。它的代价是能不能玩取决于有没有人移植过这一款。

**第二，PortMaster 的规模由移植者数量决定。** 199 位移植者撑起 1,500 多款游戏与 40 款设备（portmaster.games）。这种模式的门槛在移植与打包，不在服务器。想判断一台冷门机器值不值得买，先看它有没有被这个清单收录。

**第三，安卓掌机的转折点在转译层。** Zaviya 用 FEX 加 ARM64 版 Proton 跑 x86 游戏（github.com），DroidDeck 直接装真 Steam 客户端（droid-deck.dev）。两条路都把 x86 游戏变成安卓能执行的东西，代价是要动系统设置，DroidDeck 在 Android 14 以上需要关掉子进程限制。

**第四，兼容率要按游戏类型分层看。** 中小型独立游戏八九成、3A 看运气（现场记录），这个分布与图形特性、反作弊和驱动成熟度相关【推断】。把能跑当成单一指标会误导购买决定，先看自己要玩的那几款有没有实测记录。

**第五，iOS 的约束是代码生成权限。** 苹果不允许 App 在运行时生成可执行代码，能上 App Store 的模拟器只能走解释执行或预先翻译。Delta 停在一代掌机与 16 位主机（apps.apple.com），S2Arm 用静态重写加自签名绕开这条限制（s2arm.com）。绕开的代价是安装流程变长、每年续签。

**第六，正版化路线把法律问题前置解决。** 心动网络收购 IP 之后做原生移植（官方汇总页记录），这条路的成本在授权谈判，不在技术。它说明移植生态里最贵的一环常常是权利【推断】。

**第七，设备分层对应不同的等待成本。** 百元机开机即玩，安卓机要装包、改设置、等转译，Steam Deck 最贵但最省事。选哪一档，取决于愿意为少折腾付多少钱。

### 可迁移的方法

1. 挑掌机先定层级：要秒开就选 Linux 原生移植，要玩 Steam 库就选能跑 Proton 的方案。
2. 买安卓掌机前查 GPU 型号，DroidDeck 的推荐线是 Adreno 730 及以上（droid-deck.dev）。
3. 用 PortMaster 的游戏清单反查：想玩的游戏有没有人移植过。
4. 做移植类项目先算清签名与授权两道门槛，再评估工作量。
5. 记录兼容率时按游戏类型分组，写清测试机型与版本。

### 边界与提醒

八九成的兼容率是个人实测（现场记录），没有公开的测试清单，机型、版本与设置都不明确。换一台机器、换一个驱动版本，结果可能不一样。

Zaviya 的安装会写卡并替换设备的 bootloader，README 要求先备份原厂 bootloader 与数据（github.com）。DroidDeck 明确写着反作弊游戏多数不能联机，也没有 iPhone 版本（droid-deck.dev）。S2Arm 需要自备游戏文件与 Apple ID 逐台签名，页面声明与任天堂、苹果没有隶属或授权关系（s2arm.com）。

官方记录说 App Store 里的模拟器上限停在 NDS / 3DS，实际页面上 Manic EMU 列出了 3DS、GameCube、Wii 与 PSP（apps.apple.com），两处说法不一致。TestFlight 页面核验到的是名额已满，正式发布时间没有公开（testflight.apple.com）。

## 06 张峻玮：在 iPhone 里运行 Linux 沙盒

**身份**：官方汇总页给出的是即刻主页，公开页面显示昵称为「六根清净」，发布内容围绕 SaaS、Agent 与 Claude Code 的使用方式，没有写职业（m.okjike.com）。他的起点写在官方记录里：想把 Blender 放进云端沙盒，算下来太贵（官方汇总页记录）。
**分享对象**：在 iPhone 本地给 AI 塞进一个 Linux 沙盒，以及他为此参考、对比的几个项目。
**关键词**：端侧沙盒、AOT 翻译、JIT 限制、图形桌面。

### 他讲了什么

**动机。** 云端沙盒按使用时长计费，跑一次 Blender 的账算下来不划算，他把方向转到手机本地（官方汇总页记录）。现场描述的是这条路线的取舍：省下的是租算力的钱，付出的是内存与系统限制。

**参考对象。** OpenMinis 是他参考的开源 Agent：GPLv3 许可，iOS 与 Android 双端，iOS 侧跑的是 iSH 的 ARM64 分支，Android 侧用 PRoot，沙盒里是 Alpine Linux，模型接 Claude、GPT、Gemini，用自带密钥（github.com）。官方记录里列出的同类项目还有 LinuxRunner，仓库写明只运行 Linux 用户态程序、不启动内核，JIT 可选，自称比 UTM 快 10 到 15 倍，Hyprland 桌面需要 8 GB 内存与 Arch Linux ARM（github.com）。

**他自己的版本。** 参照 OpenMinis 的做法，他做了一个带图形桌面的本地沙盒（官方汇总页记录）。这一件没有公开仓库，现场展示的是运行效果。

**两个性能突破。** crate-ios 用 Rust 写了一个 arm64 到 arm64 的翻译器，把大多数客户机指令原样搬到宿主代码，只重写涉及机器的部分；Mac 上同一段基准，QEMU 的 TCG 用 130.5 秒，crate 用 24.5 秒；虚拟机里跑 Ubuntu 26.04 的 GNOME 桌面、Debian 13 与 Arch Linux ARM，图形经 virglrenderer、ANGLE 与 MoltenVK 转到 iPhone 的 GPU；它需要 JIT，靠内置的 StikJIT 或 StikDebug 打开，安装包是无签名 IPA，要自己签名（github.com）。另一件是两仪：构建时把 Android 的代码 AOT 翻译成 ARM64 本机指令，运行时不需要 JIT，iOS 上约 3 秒启动完整的 Android 13，免费，作者 weishu 也是 KernelSU 与 VirtualXposed 的作者（twoyi.app）。

**他自己的复盘。** 他承认手机本地沙盒目前跑不通大众商业产品：要与有限的内存和 iOS 的后台限制周旋，还要过 App Store 的审核；「云端能开无数个沙盒，本地开两个就完了，这点上 Manus 确实是版本 T0」（官方汇总页记录）。他仍然看好端侧模型成熟之后「推理与沙盒全离线」的终局（官方汇总页记录）。

### 关键点分析

**第一，成本是这条路线的起点。** 云端沙盒按使用时长计价，跑图形负载时账单增长得很快。把运行放到本地，等于把一笔持续支出换成一次性投入与设备占用，账要按自己的使用频率来算。

**第二，三条技术路线的差别在什么时候翻译。** iSH 用解释执行，两仪在构建时就把 Android 预编译成 ARM64 指令（twoyi.app），crate 在运行时做二进制翻译（github.com）。翻译得越早，启动越快；翻译得越晚，能跑的软件越宽【推断】。

**第三，iOS 的限制集中在代码生成。** 系统不允许 App 在运行时生成并执行代码，JIT 只在调试器附着的情况下放开。crate 因此只能发布无签名 IPA，由使用者用自己的 Apple 账号签名后再打开 JIT（github.com）；两仪选了 AOT，绕开这条限制（twoyi.app）。

**第四，GPU 加速决定桌面能不能用。** crate 把客户机的 OpenGL 经 virglrenderer、ANGLE 与 MoltenVK 转到 Metal，桌面合成与 3D 应用才有可用帧率（github.com）。没有这一层，虚拟机里的桌面只能算打开了。

**第五，内存与后台是本地沙盒的物理上限。** iOS 会在内存紧张时终止后台进程，沙盒里的桌面与编译任务都属于会被清理的对象。他的复盘说云端能开很多个沙盒、本地开两个就到头（现场记录），这句话说的是资源，也是系统策略。

**第六，分发环节把项目挡在商业产品之外。** 上架 App Store 要过审核，而 JIT 与虚拟机这类能力很难通过；两仪与 crate 都走侧载（twoyi.app、github.com）。OpenMinis 能上架，靠的是 Alpine 用户态沙盒这套形态（github.com）。

**第七，他的结论把前提写在端侧模型上。** 「推理与沙盒全离线」需要模型本身能在手机上跑（官方汇总页记录）。这一步没成熟之前，本地沙盒省下的是算力租金，省不下网络依赖。

### 可迁移的方法

1. 动手前先算三个月的云端账单，用这个数字决定本地方案值不值得做。
2. 按需不需要 JIT 筛方案：要 JIT 就要准备签名与调试器附着的流程。
3. 拿同一段基准在自己设备上跑一遍，再相信快几倍的说法。
4. 图形桌面先跑通一个 OpenGL 应用与一个浏览器，再谈生产力。
5. 侧载分发要提前写好签名、续签与数据迁移的步骤。
6. 把还需要联网的环节列成清单，避免把端侧说成完全离线。

### 边界与提醒

他自己的那个带图形桌面的版本只有官方记录与现场描述，没有公开仓库，功能范围与性能都未能核验。即刻页面也没有项目链接（m.okjike.com）。

crate-ios 的 5 倍数字来自仓库自己的基准：Mac 上 QEMU 的 TCG 130.5 秒对 crate 的 24.5 秒（github.com）。这是单一基准的结果，换负载、换设备都会变。iPhone 上运行需要 JIT、需要一台 Mac 完成首次签名，公开的测试机是 iPhone Duo 与 iOS 27.1。

两仪 iOS 版只跑 Android 13，不支持 32 位应用，依赖特定设备或带加固的应用可能装不上（twoyi.app）。iOS 的内存与后台限制没有公开的量化数据，「本地开两个就到头」是现场说法（官方汇总页记录）。

## 07 David Jiang：一天做完的 AI 短片《该》

**身份**：Theory A 创始人，人在上海。个人站点写明他在金融、AI 与视觉表达的交界处做产品，此前在 Apple、Google X 等公司担任工程师（dj.theory-a.com）。站点列出的作品包括金融信息平台、围棋图片计分器与词向量可视化，都是可以点开就看到的东西。

**分享对象**：一支用 AI 在一天之内导演完成的中文说唱绘本短片《该》，片长 5 分钟。

**关键词**：AI 短片、视觉规则、分镜代码、逐帧合成。

### 他讲了什么

**形式。** 官方汇总页记录，他没有展示代码，直接放了成片。全片只用两种颜色：紫色蜡笔代表「想爱的」，蓝灰色方格线代表「该爱的」。这条规则从头贯到尾，观众看颜色就知道画面在替哪一边说话。

**内容。** 官方记录的画面节点按顺序排下来是：折断的蜡笔、琴凳上的戒尺、病猫的账单，账单旁边那句话写「你越爱什么，什么就成了别人的把手」；再往后是 30 年房贷与职场跑步机；结尾把「该」字分开来讲，「该爱的就是欠着的爱，不欠谁的爱才是你自己的」，最后一句是「海是紫色的，然后我也想再画一次海」。

**工艺。** 制作分成三段。第一段，他把 Claude Code 当作联合导演，让它写词，也让它把分镜写成代码；第二段，调度 ChatGPT 生成统一画风的画面；第三段，用无头浏览器把画面逐帧合成，把音画之间的节拍误差控制在 4 毫秒以内（官方汇总页记录）。三段之间是脚本串起来的，人做的是判断与取舍。

**产物。** 官方记录给了两个入口：小红书的发布链接与原片直链。原片地址可以访问，返回 200，文件 82,037,141 字节，Content-Type 是 video/mp4，托管在 Vercel（dj.theory-a.com）。小红书那条短链会跳到登录页，本次读不到正文与互动数据。

### 关键点分析

**第一，两种颜色把情绪变成了可以执行的约束。** 紫色与蓝灰色各自代表一种选择，题材本身又是「想爱的」与「该爱的」这对矛盾。颜色一旦和意义绑定，每一帧该用哪种颜色就不需要再讨论，画风的统一也顺带解决了。做短片时最容易失控的是每一帧都想重新决定风格，规则的作用是在开工前就把这类决定做完。

**第二，词与分镜一起写进代码，省掉一次翻译。** 让模型写词、再让另一个环节把词配到画面上，中间的转述会丢失节拍与停顿。他把两件事放在同一份脚本里，词的长度、换行位置与分镜的时长可以一起算。这个做法对做演示视频、讲解片同样成立：文字与画面的时间轴共享同一份数据。

**第三，逐帧合成让节拍变成可以计算的量。** 用无头浏览器渲染每一帧，意味着帧数、每帧停留时长、切点位置都写在程序里，可以反复重跑，也可以在改一句词之后只重算受影响的那一段。4 毫秒这个数字只有在逐帧合成的前提下才有意义，靠手动剪辑对不上这个精度。

**第四，绘本风格压住了生成画面的不稳定。** 蜡笔线条与方格纸的容错程度高，模型的轻微走样混在线条里不容易被发现；写实风格一旦手指、文字或光影出错就会立刻露馅。选一个对误差宽容的画风，等于把重试次数降下来，这是一天能做完的前提之一。

**第五，短片的说服力来自结构，画面数量只是材料。** 官方的复述里，真正被记住的是那几个具体的物件与那句点题的话，镜头数量没有被提起。把 5 分钟分成十来个物件与场景的清单再按情绪排序，比先生成几百张图再挑要省力，也更容易在改稿时保持整体。

**第六，一天是制作时长，之前的准备不算在里面。** 会写脚本、会用无头浏览器、知道怎么让两个模型分工，这些能力不是当天获得的。把「一天做完」当成排期参考时，需要把工具熟练度这一项单独算进去，否则同样的流程换一个人做，时间会拉长好几倍【推断】。

### 可迁移的方法

1. 开工前先定一条视觉规则，例如只允许两种颜色、一种线条；规则写下来，后面每一帧照着执行。
2. 把词、分镜、时长写进同一份脚本，让文字与画面共用一条时间轴，改词时只重算受影响的那一段。
3. 用无头浏览器逐帧渲染，把帧率与每帧停留时长写成参数，输出成图片序列后再合成音频。
4. 题材允许的话优先选对误差宽容的画风，例如手绘、拼贴、版画，减少返工次数。
5. 先把 5 分钟分成十来个物件与场景的清单，排出情绪高低，再交给模型生成画面。
6. 成片同时留一份直链文件与一份平台版本，平台版的封面与标题按平台规则单独准备。

### 边界与提醒

4 毫秒的节拍误差只有官方记录，没有第三方复现，也没有公开的工程说明。这类数字依赖具体的音频、帧率与合成方式，换一套工具链未必还能达到。观众在手机外放的情况下，也很难分辨这个量级的差别。

## 09 elioWang：mcp-server-nuxt 与静态解析

**身份**：GitHub 账号 rynx-cc，公开资料写着名字 rynx.z、所在地杭州，账号 2026 年 10 月 20 日创建，公开仓库 6 个（api.github.com）。官方汇总页只给了他的 GitHub 主页链接，除此之外没有职业介绍，工作单位未能核验。

**分享对象**：他开源的 MCP 服务器 mcp-server-nuxt，用静态解析让 Agent 读懂一个 Nuxt 项目的路由、布局、中间件与后端接口。

**关键词**：MCP、Nuxt、静态解析、路由解释。

### 他讲了什么

**问题。** 官方汇总页记录，通用 Agent 读 Nuxt 项目时容易迷失在三件事上：文件路由把目录结构翻译成 URL 的规则、自动导入让组件与组合式函数不需要写 import、多层 Layer 覆盖让同一份配置有多个来源。官方的 DevTools MCP 能给出准确的答案，但必须先装依赖、起开发服务器。

**做法。** 他的工具走纯静态解析，刚 git clone 下来、还没装 node_modules 的项目也能直接跑（官方汇总页记录）。仓库首页写的第一句就是「不需要开发服务器，不需要 nuxi prepare」；实现上读 Nuxt 自己的配置加载器与 .nuxt/ 目录的输出，读不到时退回源码解析（github.com）。这与 DevTools 类服务器的差别在启动条件：那类工具要求应用正在运行，这个工具只要求有一份代码。

**接口。** README 写明提供 34 个工具与 7 个只读资源。工具按路由、Nitro 服务端、组件与自动导入、项目与配置、质量与检索分成五组。核心的 explain_route 接受一个 URL，返回命中的页面文件与路由模式、父级页面、布局、中间件的执行顺序、页内 useFetch 这类数据获取调用的位置，以及对应的 Nitro 接口文件与请求方法。

**资源。** 7 个资源用固定 URI 提供大块可缓存的内容，包括项目概览、路由表、解析后的配置、模块清单、Layer 层级、自动导入清单与生成的类型（github.com）。自动导入与类型这两个资源要求 .nuxt/ 目录存在，其余资源都能退回源码读取。

**权限与平台。** 带写入能力的六个工具默认停在 dryRun，只返回计划生成的文件或配置差异，真正写入需要把 dryRun 设为 false，并且服务启动时带上 MCP_NUXT_ALLOW_WRITES 环境变量或 --allow-writes 参数（github.com）。许可为 MIT，TypeScript 编写，2026 年 11 月 9 日创建，到 11 月 25 日有 4 个星标、1 个 fork（api.github.com）。README 写明要求 Node.js 18 以上，只在 macOS 与 Linux 上测试过，Windows 尚未官方支持。

### 关键点分析

**第一，静态解析换掉了启动条件。** DevTools 类 MCP 服务器靠运行中的应用回答，代价是 Agent 必须先能起服务，依赖装不上、端口被占、环境变量缺失都会卡在第一步（github.com）。静态解析把这一层门槛去掉了，代价是拿不到运行时的真实行为，例如某个中间件在特定条件下提前返回。两种方式回答的不是同一类问题。

**第二，explain_route 输出的是解析结论。** 大多数同类工具只告诉你仓库里有哪些路由，这个工具回答「有人打开 /users/42 时会发生什么」，并且把页面、父级页面、布局、中间件顺序、数据获取与后端接口串在同一条结果里（github.com）。这种形状让 Agent 不必自己推理目录约定。中间件按运行顺序返回，全局在前、具名在后，捕获所有参数以数组形式给出。

**第三，Layer 覆盖顺序是通用 Agent 最容易读错的地方。** README 把覆盖顺序写成「项目 > layers/* > 更早的 extends > 更晚的 extends」，并给了一个查询层级顺序的工具（github.com）。目录同名文件在不同 Layer 里的优先级，靠读文件树是看不出来的。凡是支持 extends 的框架，这类顺序都需要工具来回答。

**第四，写入能力默认关掉是一个可以照着做的设计。** 六个写工具先返回计划与差异，需要环境变量与参数两处同时打开才会改动文件，配置修改还会返回 diff（github.com）。Agent 误改代码是这类工具最常见的风险，把默认值设成只读，把开关放在启动命令里，比在提示词里叮嘱更可靠。

**第五，工具数量与资源划分需要一起看。** 34 个工具覆盖到迁移检查、类型检查、打包依赖、SSR 风险这类细项，7 个资源承担大块可缓存的内容（github.com）。工具回答具体问题，资源提供背景。工具多的代价是选择成本：Agent 需要在 34 个名字里挑一个，命名的一致性与描述的质量直接决定它挑得对不对。

**第六，仓库描述与文档已经不一致。** 仓库简介写的是 22 个工具与 7 个资源，README 写的是 34 个工具（api.github.com）。项目从创建到 11 月 25 日只有半个多月，功能在快速增加。使用者以 README 为准，遇到工具名对不上时先看版本与提交时间。

### 可迁移的方法

1. 给 Agent 写框架类工具时，先确定回答哪类问题：仓库结构、运行结果、还是某次请求的全链路，三者需要的实现方式不同。
2. 把「打开某个 URL 会发生什么」做成一个入口，把页面、布局、中间件、数据获取与后端接口放进同一条结果，减少 Agent 的推理步骤。
3. 有覆盖机制的框架，单独提供一个查询优先级的工具，把顺序写成可以读到的结论。
4. 所有写操作默认 dryRun，真实写入要求启动参数与环境变量同时到位，返回结果附上 diff。
5. 工具与资源分工：需要反复读取的大块内容做成资源，需要按参数查询的做成工具。
6. 在 README 里写明平台支持范围与测试过的系统，未支持的平台直接说清楚。

### 边界与提醒

仓库创建于 2026 年 11 月 9 日，到 11 月 25 日只有 4 个星标、1 个 fork，没有外部使用者反馈（api.github.com）。这类项目在早期改动的频率很高，工具名与参数都可能变，接口文档需要跟着版本读。

静态解析的答案是源码层面的推断：Nuxt 的配置可能由函数生成，也可能读环境变量，源码回退与真实运行时之间会有差距（github.com）。配置解析依赖目标项目的 @nuxt/kit，目标项目没装依赖时走源码解析，这条路径的准确性 README 没有给出覆盖范围。

Windows 未官方支持，只测过 macOS 与 Linux，这会让一部分使用者直接放弃（github.com）。工具数量多也带来选择成本，34 个工具里哪些真的被用上，需要使用者自己统计。仓库简介仍写 22 个工具，文档与元数据不一致这件事，说明维护节奏快过整理节奏。

## 10 火箭君CC：本地 Markdown 与 AnyDoc

**身份**：独立博客「效率火箭」的作者，站点副标题写「火箭君的新博客」，内容集中在效率工具与个人数据存放方式，最近一个月的文章包括 1Password 7 的本地密码库、mem.ai 关闭服务之后的数字记忆，以及把 Raindrop 书签接进 MCP（xlrocket.blog）。他在 2026 年 11 月 12 日写过一篇 AnyDoc 的介绍，比这期分享早一周。

**分享对象**：以本地 Markdown 与 Obsidian 为核心的资料保存方式，以及把 Word、PDF、PPT 转成 Markdown 的开源工具 AnyDoc。

**关键词**：本地优先、Markdown、文档转换、WebAssembly。

### 他讲了什么

**立场。** 官方汇总页记录，他借上一场 David 歌里的「软肋」来讲本地优先：数据保存在云端就成了软肋，不如全部以 Markdown 存在本地的 Obsidian 库。同一场里，他演示的工具都是为了把这个库喂得更饱。

**工具。** Firecrawl 用 Rust 开源的 AnyDoc，到 11 月 25 日有 23,711 个星标、1,555 个 fork，MIT 许可，2026 年 8 月 3 日创建（api.github.com）。官方记录写的星数是 2.3 万以上，与接口数据一致。README 的定位是把 Word、PowerPoint、Excel、OpenDocument、RTF、EPUB、CSV 与 PDF 转成干净的 GitHub 风格 Markdown，并提供 Node.js、Python 与浏览器三套绑定。

**三种用法。** 一是命令行：npx 调用时按平台下载预编译的可执行文件，输入文件、输出到标准输出或指定文件。二是 Agent Skill：一条 npx skills add firecrawl/anydoc 装进 Claude Code、Codex、Cursor 这类客户端，让 Agent 遇到文档时自己去转。三是 WebAssembly 版本，官方给出的网页版把转换放在浏览器里跑，文件不离开本机（firecrawl.github.io）。

**覆盖与速度。** 官方记录说它覆盖全部 14 种办公与电子书格式，连 Office 97 到 2003 的二进制老文档也支持，中位耗时 4.7 毫秒，比微软的 MarkItDown 快很多。README 的基准表给的数字是 4.4 毫秒中位、覆盖 14 种格式里的 14 种，测试机是 Ryzen 9 9950X3D、Windows 11、64 GB 内存，同表的 MarkItDown 覆盖 6 种、中位 134.8 毫秒（github.com）。

**不含 OCR。** 官方记录说它原生不含 OCR，扫描件需要外接识别服务。README 写得更具体：纯文本 PDF 在本地转换，遇到扫描页或纯图片页会返回 NeedsOcr 错误；要处理这类文件，得主动打开 ocr 选项，把整份文档送到 Firecrawl Parse，再由它返回同样的 Markdown（github.com）。

**同类。** 台下古思为补充了 LlamaIndex 开源的 LiteParse，同样用 Rust 编写，到 11 月 25 日有 13,372 个星标，Apache-2.0 许可（api.github.com）；官方记录说其中的轻量小模型本地 OCR 后端由他贡献。

### 关键点分析

**第一，本地优先的实际内容是数据形状。** 把资料存成 Markdown 文件，每篇一个文件，目录就是结构，换编辑器不必迁移（官方汇总页记录）。这种形状的代价是没有数据库带来的检索与统计能力，收益是十年后还能打开。判断一个工具值不值得长期用，先看它退出时能不能把数据完整带走。

**第二，单一序列化器解决了格式之间的不一致。** AnyDoc 把每种格式先解析进一个共享的文档模型，再统一渲染成 Markdown，README 的说法是「一套输出对应所有格式」，表格转义、脚注、标题锚点的修正只需做一次（github.com）。这对批量处理很重要：混合收到 docx、pptx、rtf 时，输出的结构应当一致，否则下游的切分与检索要写多套规则。

**第三，WebAssembly 版本把「不上传」变成可以验证的事实。** 官方给的网页版在浏览器里跑同一份 Rust 代码，文件不经过服务器（firecrawl.github.io）。对合同、财务报表这类材料，「不上传」这句话光靠声明没有说服力，能在断网状态下完成转换才算数。这个形态也让「先试一次再决定要不要装」变得没有成本。

**第四，无 OCR 是一处明确的能力边界。** 扫描件会直接报错，不会返回一份看起来能用、实际缺字的文本（github.com）。这种处理方式对流水线友好：错误可以被捕获、被记录，剩下的文件继续跑。代价是扫描件必须另找服务，而外接服务意味着文件要离开本机，本地优先的主张在那一步会中断。

**第五，速度来自不加载模型。** 中位 4 毫秒这个量级，前提是解析过程里没有神经网络参与（github.com）。纯 Rust 的解析器在启动与内存上都占优势，适合放在批量脚本里跑上万个文件。需要理解版面、识别手写的场景，它帮不上忙，那是另一类工具的位置。

**第六，基准表需要看测试条件。** README 写明质量分由 Claude Sonnet 5 做盲评，以 LibreOffice 渲染的前六页图片为标准答案，每对输出交换位置各判一次，共 482 次判定；速度是每份文档一次热转换（github.com）。这些条件说明结果可复现，也说明分数与语料有关：换一批文档，排名可能变化。

### 可迁移的方法

1. 个人资料统一存成 Markdown，一篇一个文件，目录分主题，附件与正文同目录存放。
2. 批量转换文档前，先拿五种格式各一份做小样本，检查表格、脚注与代码块有没有丢失。
3. 需要保密的文档用浏览器里的 WebAssembly 版本转换，断网验证一次，确认文件没有出网。
4. 转换失败的文件单独记录下来，不要混进成功队列，扫描件按 NeedsOcr 归类后统一处理。
5. 给 Agent 装上转换类 Skill，让它遇到 docx、pptx 时先转成 Markdown 再读，避免逐页截图。
6. 把基准表里的测试机配置与语料规模抄进自己的评估记录，换环境后重跑同一批文件。

### 边界与提醒

4.7 毫秒来自官方汇总页，README 的基准表写的是 4.4 毫秒，两个数字都指向同一台测试机上的中位值，差异可能来自测量批次（github.com）。这类微秒级的差别在实际使用里感觉不到，真正影响体验的是大文件与复杂表格。

外接 OCR 会把整份文档送到 Firecrawl Parse，README 写明 Parse 不支持只选部分页面（github.com）。对扫描件多的场景，「本地优先」在那一步不成立，需要提前跟使用者说清楚。

LiteParse 的 OCR 后端由古思为贡献这一条只有官方记录，本次只核对了仓库的星标、许可与语言，没有逐条读它的 OCR 实现。两个工具定位接近，选哪一个要看自己的格式分布与是否需要 OCR。

### 关键点分析

**第一，产品调研要看真实流程，不看宣传图。** Mobbin 收的是上线产品的完整交互，包括空状态、表单校验、支付步骤这些不常被放进宣传材料的部分（mobbin.com）。做功能设计时，能查到同类产品在同一个环节怎么处理，比凭印象画原型省下大量返工。代价是这类库通常按订阅收费，采购前先看使用频率。

**第二，新手引导值得单独当成一门手艺。** UserOnboard 的每一篇都按「第一步看到什么、第二步要求什么、什么时候才让人做成第一件事」这个顺序讲（useronboard.com）。这套顺序可以直接迁移到自己的产品：把首次使用的路径截图排成一列，逐屏标出「用户此刻需要决定什么」。多数流失发生在第二屏到第三屏之间，这一段往往没人认真做过。

**第三，榜单是选题的输入，判断仍要自己做。** 刷各国榜单能看出某个品类在哪个市场已经饱和、在哪个市场还是空的（官方汇总页记录）。榜单只给排名，不给留存与收入，靠它判断需求强弱容易失手。比较稳妥的做法是把榜单当线索，再去应用商店读最近三个月的差评。

**第四，失败案例的价值在于校准预期。** 失败博物馆把 Humane AI Pin、Rabbit R1 与 249 美元的 Friend 二代放在同一个专区（官方汇总页记录），这几件产品都曾被大量报道。看它们的问题出在硬件、场景还是定价，能让自己的方案少走一段。这类展览的叙事强调戏剧性，读者容易忽略工程细节。

**第五，浏览体验的损耗是可以修掉的。** 外链拦截页每次多花几秒，一天几十次之后就是一段被浪费的注意力；这个油猴脚本直接跳过去（greasyfork.org）。Cloudhiker 用随机跳转替代算法推荐，33,969 个站点由人一个个看过再收进来（cloudhiker.net）。这类小工具不解决大问题，却决定了一个人每天愿意在网上待多久。

**第六，人工策展与算法推荐是两种不同的信息源。** Cloudhiker 的页面自己写着没有爬虫、没有算法、没有排行榜，站点分类只有二十个（cloudhiker.net）。Whimsical Web 的收录标准更窄，只看交互有没有意思（whimsical.club）。这两种库的共同点是小而稳定，适合在需要灵感时翻一翻，不适合当作每日信息流。

### 可迁移的方法

1. 给自己建一个「界面流程」收集夹，截下同类产品的关键三步，附一句「它在这里解决了什么」。
2. 把自家产品的首次使用路径逐屏截图，排成一列，标出每一屏要用户做的决定，找出多余的一屏删掉。
3. 查出海选题时同时看榜单与差评：榜单给排名，差评给具体没被满足的需求。
4. 每月读两个失败案例，写下它的场景、定价与替代品，再对照自己的方案改一处。
5. 装一个跳过外链提示的脚本，把常用站点的拦截页列出来，逐个确认跳转是否正常。
6. 把人工策展类站点放进单独的收藏夹，每周随机点开三个，记下其中一个可以借鉴的交互。

### 关键点分析

**第一，需求侧的输入被压到极短。** 两个入口分别是一句话与一条动效视频（官方汇总页记录）。视频这一路带的是节奏、转场与层级，这些用文字描述最容易走样。代价是视频不携带业务规则，Agent 必须靠追问或默认值补齐，补出来的东西未必是用户想要的。【推断】

**第二，分工写在角色上，不写在流程图上。** 四个 Agent 共享同一份 brief 与项目上下文，切换本地与云端时这些内容跟着走（air.build）。好处是每条消息都能对上「这件事归谁」；难处在交接面，产品把需求写清楚、设计把屏幕画出来、工程把它实现，中间任何一步理解出错，后面都会放大。

**第三，审核是可以程序化的一段。** 四步里最难的是 Respond 与 Fix：读反馈、回复、分派、修好、重提（air.build）。多数团队卡在这里，因为拒审理由写得笼统，要有人去查条款、改截图、补说明。这件事规则性强，适合交给 Agent；判断「Guideline 4.2 最低功能要求到底缺什么」仍然要人来定（air.build 的资源页把 4.2 单列成一个主题）。

**第四，定价把模型成本转到用户身上。** Basic 档 10 美元/月自带密钥，API 用量由用户自己的服务商结算（air.build）。这一档把最不可控的推理开销挪出了订阅，价格才压得住。对使用者来说，成本结构从一笔月费变成月费加 token 账单，用量大时总额会超过上一档。按月结算的订阅把不确定性留给服务方，按量结算把不确定性留给使用者，选档之前先估一周的实际消耗。

**第五，邮件作为 A2A 的载体，靠的是普遍性。** 几乎所有 Agent 都能收发邮件（官方汇总页记录），跨产品交接因此不需要双方先谈接口。代价在延迟与结构化程度：邮件是异步的，附件与正文格式各家理解不一致，交接失败时排查链条很长。真要把它当成协议来用，邮件里最好固定四个字段：任务、上下文、验收标准、回复期限。

**第六，老板这个角色的工作内容变了。** 他的原话是「少插手、当好老板」（官方汇总页记录）。这句话换成具体的动作，就是把注意力从写代码转到写清楚要什么、验收什么。这需要一套自己的验收清单，否则「老板」只剩下点头。他的做法是把这套心得压成一句话，每天的具体动作是少改一行代码、多写一句验收条件。

### 可迁移的方法

1. 把需求写成一段 brief，固定包含目标用户、首版范围、必须原生实现的三件事，交出去之前自己先读一遍。
2. 给每个 Agent 一个角色名与一句职责，交接时只传「上一棒交付了什么、下一棒要产出什么」。
3. 拿动效视频当参考时，在同一条消息里补三句文字，说明节奏、层级与转场。
4. 把 App Store 的拒审理由建成自己的条目库，按条款编号归档，下次遇到同类问题直接调用。
5. 先用自带密钥的档跑一周，记录 token 消耗与产出，再决定要不要升档。
6. 建一个交接邮件模板，写清任务、上下文、验收标准与截止时间。

### 边界与提醒

官网仍在等待名单阶段，早期访问有名额限制（air.build）。本次没有实际提交过应用，审核自动化在真实拒审场景里的表现无法核实。

后端容器平台目前只在美区提供，测试期免费，之后可以导出成兼容 Cloudflare 的部署（air.build）。国内团队要用这一部分需要另找方案。

## 13 Victoria Zhang：美东西海岸的 AI 温差

**身份**：Victoria Zhang 今年 6 月从新加坡离职，之后实地走访了硅谷、波士顿、纽约与国内几个城市。她现在做两件事：探索跨境 AI Builder 的产研连接，以及把大厂出海方法论按模块交付给 B 端企业与一人公司（OPC）（官方汇总页记录）。她的主页指向小红书，本次打开只到登录页，没有读到帖子正文（xhslink.cn）。

**分享对象**：一份按城市划分的美国 AI 采纳情况观察，从硅谷的乐观、波士顿的分裂，到纽约的矛盾。

**关键词**：AI 温差、实地走访、出海方法论、一人公司。

### 她讲了什么

**一条从新加坡出发的路线。** 官方记录给的起点是今年 6 月离职，之后她走的地方包括硅谷、波士顿、纽约与国内（官方汇总页记录）。这条路线同时覆盖三种生态：硅谷是产品与资本的源头，波士顿是高校与实验室，纽约是金融与行业客户。

**硅谷全员乐观。** 官方记录用的词是「全员乐观」（官方汇总页记录）。这四个字在访谈场景里通常指受访者对 AI 会不会改变自己所在行业没有疑问，分歧只在于谁做得更快。【推断】

**波士顿五五开。** MIT 不少实验室里，一半人以 anti-AI 为傲；她去看的一个 3D Maker 实验室直接回复「No, we don't use any AI at all.」（官方汇总页记录）。这句英文是这次分享里最有画面感的一条证据：拒绝得很干脆，连「试过但没用」这种缓冲都没有。

**纽约的矛盾。** 华尔街一边用 AI 提效，一边焦虑被替代；美东的建制派整体带着「老钱」的防御底色（官方汇总页记录）。同一个人可以在工作流里用 AI 写备忘录，同时在饭桌上说这东西靠不住。

**她在交付什么。** 官方记录写她正在探索跨境 AI Builder 的产研连接，以及把大厂出海方法论做成可以按模块交付的东西，客户是 B 端与一人公司（官方汇总页记录）。OPC 是 one person company 的缩写，指一个人撑起整条业务线的团队形态。

### 关键点分析

**第一，温度差来自各自关心的问题。** 硅谷关心下一波产品位在哪里，波士顿的实验室关心能不能发表、能不能复现、训练数据有没有污染，纽约关心岗位与合规。三个地方回答的「AI 好不好用」其实是三个不同的问题。【推断】把三个地方的回答混在一起统计，得到的平均数没有意义。

**第二，anti-AI 在学术圈带着身份色彩。** MIT 的实验室里一半人以不用 AI 为傲（官方汇总页记录），重点在「为傲」这两个字。当一个群体的声誉与手工完成绑在一起，使用工具就容易被读成能力不足。在这种氛围里，愿意承认自己在用 AI 的人往往已经拿到了结果，样本本身带有选择误差。

**第三，3D Maker 实验室的回复值得当样本。** 原文是「No, we don't use any AI at all.」（官方汇总页记录）。这类实验室的产出是实体物件与制作工艺，AI 能帮的地方集中在概念图与参数搜索，碰不到机床与材料。拒绝的合理性来自工作内容。换成写代码、做数据的实验室，同样的回复就很难成立。判断一个「不用」是不是认真的，看去掉 AI 之后他们的产出形态会不会变。

**第四，纽约的矛盾是可以经营的。** 一边提效一边焦虑（官方汇总页记录），意味着采购决策会同时受效率指标与人力保护影响。向这类客户卖工具，需要把「省下多少小时」与「不会让谁失去岗位」放在同一页上。【推断】只讲效率，采购会被人力部门的顾虑拖住；只讲不减人，预算又批不下来。

**第五，走访的价值在原话。** 二手报告能给趋势，原话能给出语气：谁在兴奋，谁在防御，谁在敷衍。她引用那句英文回复，比任何一份调研报告的百分比都更能说明一个实验室的态度。缺点是原话不好量化，样本一多只剩下印象，需要和清单式的记录配合着用。

**第六，「老钱」的防御来自积累得久。** 美东建制派的资源与关系积累得久，不必靠押注新赛道来兑现收益（官方汇总页记录）。这类客户更愿意在既有业务里做增量改造，把 AI 接进已有的流程。【推断】对这类客户的销售节奏因此更慢，试点周期长，决策链条上每一层都要被说服。

### 可迁移的方法

1. 出门前按资本、学术、行业客户三类把城市分组，每一类至少约到三个人。
2. 每次访谈固定问三个问题：最近一次用 AI 做了什么、在哪一步放弃、如果它明天消失会怎样。
3. 当场记录原话，回程后再把原话归到态度、场景与阻碍三栏，避免把印象写成结论。
4. 把「不用 AI」的回答单独建一栏，写清对方的产出形态与工作流，区分立场与工作性质。
5. 面向 B 端交付方法论时按模块切分：选题、冷启动、增长、合规，每块配一份可执行的清单。
6. 面向一人公司交付时把清单压到一页，只留「今天做什么、明天验证什么」。

## 14 草原张（Naren）：TOI-7930 与业余科研

**身份**：草原张的网络代号是 Naren，主页是 paradigmroadmap.com，本次打开时页面的标题写「月球摄影档案 · Lunar Photography Archive」，正文由脚本渲染，只读到标题（paradigmroadmap.com）。他这次讲的是一位 28 岁西班牙产品经理 Pavel Rabtsevich 的业余科研过程（官方汇总页记录）。

**分享对象**：一个没有天文学背景的人，用 Claude Code 与 Codex 在公开望远镜数据里找到两颗凌日候选体、拿到官方编号的过程与方法。

**关键词**：业余科研、TESS 光变数据、可证伪、TOI 编号。

### 他讲了什么

**对象与工具。** 主角是 28 岁的西班牙产品经理 Pavel Rabtsevich，没有天文学背景，用 Claude Code 和 Codex 写了上千个脚本（官方汇总页记录）。他筛的是 NASA TESS 望远镜的公开光变数据，规模是 12.6 万多颗恒星（官方汇总页记录）。

**找到的目标。** 目标是 116 光年外的晚 K 型矮星 TIC 4206066，官方流水线漏掉了两个凌日候选信号；主候选体的周期 3.18 天，半径约 1.38 倍地球半径，7 年里 22 次凌日全部准点（官方汇总页记录）。三维演示页现在的标题是「TIC 4206066 | Two possible planets」，页面说明两颗候选行星分别处在 3.18 天与 11.13 天的轨道上，两颗都还没有被确认；页面另注明星体尺寸与轨道是按行星模型估算的，轨道距离按真实比例，星体与行星本身做了放大（tic4206066.pages.dev）。

**可证伪的那一步。** 他先把某一年的数据藏起来，只用其余年份拟合轨道，盲测预测下一次凌日的时间，再揭盲核验；随后排除食双星造成的假阳性，并到 36 个历史星表与 34 万条官方警报里查重（官方汇总页记录）。

**换来的资源。** 凭这份预印本，他拿到了 NASA TESS 台长自由支配观测时间，编号 DDT #100；11 月 6 日获授官方编号 TOI-7930（官方汇总页记录）。系外行星只按星表编号，发现者没有命名权（官方汇总页记录）。

**演示页的出处。** 三维页的署名是「Made by @p_rabtsevich」，银河背景标 ESA/Gaia/DPAC、许可 CC BY-SA 3.0 IGO，恒星数据用 HYG v4.1（tic4206066.pages.dev）。素材与数据都写了来源，这一点在业余项目里不常见。

### 关键点分析

**第一，公开数据把门槛挪到了方法上。** TESS 的光变数据是公开的，12.6 万颗恒星的规模对一个脚本来说不算大（官方汇总页记录）。难的是知道该找什么，以及怎么判断一个亮度凹陷是行星遮光、恒星自身活动，还是仪器抖动。这三类信号在单条光变曲线上长得很像，判据只能一层一层往上加。

**第二，藏起数据再预测，是整套流程里最值钱的一步。** 藏起一年、用其余年份拟合、盲测下一次凌日的时间（官方汇总页记录）。这一步把「我找到了」变成「我预测的位置上真的出现了」，两者在可信度上差一个量级。盲测的那一年数据在拟合阶段完全不可见，模型没有机会去迁就答案。

**第三，排除假阳性比发现更费工。** 食双星、背景食双星与仪器系统误差都能造出形状相似的光变凹陷。他查了 36 个历史星表与 34 万条官方警报（官方汇总页记录），这一步决定结论能不能站住。查重的结果要写成可以复查的清单，别人才走得通同一条路。

**第四，官方编号只证明被收录。** TOI-7930 这个编号 11 月 6 日授予（官方汇总页记录），它表示目标进了 TESS 的候选体目录。演示页自己写着两颗候选都没有被确认（tic4206066.pages.dev）。把编号读成「发现行星」会夸大结论。对外表述时把「候选」两个字写全，比事后解释省力。媒体转述时最容易漏掉的正是这个词。

**第五，DDT 观测时间是同行评价的信号。** 台长自由支配时间要挤进已经排满的排期（官方汇总页记录）。【推断】评审者愿意为这个目标让出时间，说明预印本里的证据链被认真读过。这条资源同时带来压力：观测窗口排上之后，候选体必须经得起复核。时间一旦排定，后续的公开观测会替所有人做检验。

**第六，上千个脚本是这类工作的真实形态。** 每筛完一轮就看结果、调判据、再跑一遍（官方汇总页记录）。这种结构让试错的成本很低，一个想法当天就能验证，不对就换下一个。代价是脚本数量涨得很快，命名与版本管理要跟上，否则过两周自己也找不到哪一版跑出了结果。

### 可迁移的方法

1. 选一个公开数据集，先把字段与单位读清楚，写一个最小脚本把第一条记录打印出来。
2. 把大目标切成能打分的小判据，每加一条判据就回头跑一次全量数据，记录通过率。
3. 留出一段「藏起来的数据」，先在其余部分拟合，再去预测被藏起来的那一段。
4. 建一份假阳性清单，把已知干扰源逐条写成检查项，每条都要给出通过或不通过的理由。
5. 出结论前做一次查重，把公开目录与历史记录过一遍，写下检索式与检索日期。
6. 把过程写成别人能重跑的预印本，数据与脚本一并附上。

## 15 Xinxia Ling：NX2Apple 与 Switch 游戏移植

**身份**：Xinxia Ling（林欣霞）是做 Switch 游戏移植工具 NX2Apple 的开发者，仓库挂在 GitHub 的 LNPANDY 账号下（github.com）。她同时是推理游戏的重度玩家，这次还带了一份解谜游戏推荐清单（官方汇总页记录）。她的 LinkedIn 主页返回 999，被登录与风控拦住，本次没有读到履历（linkedin.com）。

**分享对象**：一个把 Switch 游戏代码重写成苹果原生程序的图形化开源工具，以及它在 Apple Silicon 设备上的实际表现。

**关键词**：静态重写、Metal 着色器、图形化构建、解谜游戏。

### 她讲了什么

**工具与目标平台。** 仓库简介写「Play your own Switch games on iPhone/iPad — one-click macOS app, no terminal」，中文一句是「把 Switch 游戏装进 iPhone：图形界面一键构建，不用命令行」（github.com）。官方汇总页记录的说法是把 Switch 游戏移植到 Apple Silicon Mac（官方汇总页记录）。两处描述的目标平台不一致，本次没能澄清。

**自备游戏。** 仓库简介还有一句「Bring your own game」（github.com），工具本身不随附任何游戏，玩家要用自己手头的游戏来构建。这句话把工具与「提供盗版下载」的争议隔开了一段距离。

**它做的事。** 按官方记录，NX2Apple 把 ARM64 的 Switch 游戏代码静态重写为苹果原生指令，把着色器转译为 Metal 渲染，全程点鼠标即可构建（官方汇总页记录）。产物是一份原生程序，运行时不去模拟 Switch 的硬件。

**版本门槛。** 需要 macOS 26.6 或 27，以及 Xcode 27.2（官方汇总页记录）。首次切地图要编译着色器，会出现短暂卡顿，她把这叫作「防沉迷机制」（官方汇总页记录）。

**解谜清单。** 她推荐的第一款是 Murdoku，把数独与凶案户型推理拼在一起，一局大约 20 分钟；第二款是 Steam 上的 The Roottrees are Dead，靠复古网页搜证补全豪门族谱；第三款是 Steam 免费、文本质量很高的《婆罗洲的红珍珠》，走非线性时间线推理（官方汇总页记录）。台下 Yorkson 补充了手绘暗黑侦探解谜游戏《银松镇》（官方汇总页记录）。

### 关键点分析

**第一，静态重写与模拟器是两条路。** 模拟器在运行时翻译指令，兼容性好、开销大；静态重写把翻译放在构建阶段，产物是原生程序，运行速度接近原生。代价是每个游戏都要单独过一次重写流程，遇到自修改代码、特定硬件行为与反调试逻辑时容易卡住。

**第二，图形化界面把门槛从命令行挪到鼠标。** 仓库简介把 no terminal 写进了第一条（github.com）。这类工具的用户是玩家，装环境、编译、签名这些步骤都得藏进按钮后面。做得好不好，主要看出错时给出什么提示。提示里写清缺什么、去哪里装、装完怎么验，能省掉大半的支持请求。

**第三，真正的门槛是系统版本。** macOS 26.6 或 27 与 Xcode 27.2（官方汇总页记录），这组版本号说明工具依赖新版系统里的框架。系统没升到位的机器装不上，硬件够用也没用。她在分享里把版本号说得很具体，这类信息比功能列表更能决定别人能不能上手。版本要求写错一个数字，用户就会在第一步停住。

**第四，着色器编译的停顿是这类移植的典型特征。** 首次进入地图要把着色器编译成 Metal 能用的形态，之后依靠缓存（官方汇总页记录）。把这段等待讲成「防沉迷机制」，是这次分享里少见的、把技术缺陷说得让人记住的表达。对做工具的人来说，这种玩笑也是一种预期管理：先说清楚，抱怨少一半。

**第五，推荐清单与工具出自同一个兴趣。** 她是推理游戏重度玩家（官方汇总页记录），做移植的动力来自想在自己的设备上玩。这类项目的起点往往是个人需求，做完之后才被更多人用上。推荐清单因此不只是彩蛋，它说明了工具服务的真实场景。清单里的作品她自己玩过，推荐才有分量。

**第六，开源仓库把可信度交给别人检查。** 工具放在 GitHub 上，代码与议题都能被查看（github.com）。对「重写游戏代码」这种容易被怀疑的话题，开源是最直接的说明方式。代码公开也意味着构建流程能被复现，别人可以自己判断它究竟做了什么。问题挂在议题区，处理过程也留痕。

**第七，工具与内容分开，责任也分开。** 简介写「Bring your own game」（github.com），工具只负责转换，游戏由用户自己持有。这种分工让项目可以公开托管，也把是否符合当地法律与授权条款的判断留给了使用者。这条界线划清楚，项目才敢长期挂在公开仓库里。使用者也要为自己的选择负责，这一步没人能代劳。

### 可迁移的方法

1. 先确认目标设备的指令集与图形接口，再决定把翻译放在构建期还是运行期。
2. 把版本依赖写在仓库第一屏：系统版本、编译器版本、最低硬件。
3. 给首次编译这类长等待做可见的进度提示，别让用户以为程序卡住了。
4. 在 README 里写清哪些游戏能跑、哪些跑不了，附上失败案例与原因。
5. 把图形界面当成主要的错误处理入口，每次失败都给出一句人能读懂的原因。

## 16 Lingo：WatchWithU 与全双工陪看

**身份**：Lingo 是 WatchWithU 的作者，个人站点 sidwith.wordpress.com 的站名是「赛德SAIde」，副标题「寻找万物之间浅薄的联系」，分首页、草莓地、虚言症、求甚解、杂集、东方既白、播客、门修斯、照片几个栏目（sidwith.wordpress.com）。站点上的最新文章停在 2023 年 2 月，没有这次插件的记录（sidwith.wordpress.com）。

**分享对象**：一款用 Codex 花 10 分钟写出来的 Chrome 陪看插件，接全双工音视频接口，边看剧边问人物关系。

**关键词**：全双工、陪看、意图拒识、说话人分离。

### 她讲了什么

**一个具体的不便。** 看《大明王朝 1566》与《巴比伦柏林》时，遇到不认识的历史人物要暂停、切出去搜、再回来看（官方汇总页记录）。这两部剧一部是明史剧，一部是德剧，人物都多，停下来搜一次就会打断剧情。

**十分钟写出来的插件。** 她让 Codex 花 10 分钟写了这款 Chrome 插件，名字叫 WatchWithU（官方汇总页记录）。十分钟这个数字说明当时的范围压得很窄，先解决「能问」这一件事。

**接口与取帧。** 插件接入全双工音视频接口 MOSS-Live，以 1 秒 1 帧的频率传画面，支持外放混流下的说话人分离，也支持用语音控制播放与暂停（官方汇总页记录）。

**现场实测的意图拒识。** AI 讲解到一半，她故意喊一句「外卖放到门口」，或者口头附和「哦原来说是他」，模型都不被打断，只在真正提问时才接招（现场记录）。这一段是现场演示。

**价格与下一步。** 接口目前限时免费，后续商用大约一两毛一分钟；下一步计划适配没有字幕的播客（官方汇总页记录）。

**下一步为什么是无字幕播客。** 官方记录写下一步计划适配没有字幕的播客（官方汇总页记录）。播客没有画面可传，取帧这一路要先停用；没有字幕的时候，模型只能靠语音识别拿到人名与事件，误差会集中到转写这一段。【推断】

### 关键点分析

**第一，取帧频率决定手感。** 1 秒 1 帧意味着画面每秒只更新一次（官方汇总页记录）。对白节奏慢的剧够用，动作快或者要靠小字看字幕的场景会不够。低频率的好处是带宽与成本都低。把频率做成可调参数，遇到快节奏内容再临时拉高，是一种省钱的折中。

**第二，全双工是意图拒识的前提。** 传统语音交互是一问一答，麦克风打开时模型必须判断这句话是问题还是环境音。全双工让模型可以一直听、按需回应，插话与打断才能在同一个通道里处理。代价是模型得一直听，算力与费用按分钟累积。这也是限时免费的接口适合先做验证的原因。

**第三，拒识比识别更难。** 她拿「外卖放到门口」当测试句（现场记录），这句话语法完整、指向明确，只是对象不在剧里。模型要判断的是「这句话是对我说的吗」，属于对话对象判定。现场那两句测试句挑得准：一句是对家里人说的，一句是对剧情发的感慨，都不是提问。

**第四，说话人分离解决的是混流。** 外放时观众的声音与剧里的对白混在一条音轨上，插件要把提问从剧情音轨里分出来（官方汇总页记录）。分离得准，模型才不会把台词当成问题。混流处理不好，常见的结果是模型抢答剧里人物的台词。混流场景的评测，比安静房间里的演示更能说明水平。

**第五，语音控制把交互收进同一个通道。** 看剧时手上常常没空，用一句话控制暂停比切窗口点按钮省事，也避免了鼠标操作打断观看。这条功能看着小，实际决定了人愿不愿意在沙发上用它。手上拿着遥控器或端着杯子时，一句话比一次点击更顺手。

**第六，成本结构决定它能不能变成生意。** 一两毛一分钟（官方汇总页记录），按分钟计费意味着看得越久账单越高，连着看几集会很快累积。这个价格直接决定免费额度怎么设、什么时候该提醒用户。免费额度用完怎么提示、提示几次，都会直接影响留存。

**第七，形态选在浏览器里，安装成本最低。** 插件以 Chrome 扩展的形式存在，装完在网页播放器旁边就能用，不需要另开客户端（官方汇总页记录）。代价是它绑定浏览器内的播放场景，桌面播放器与投屏都不在覆盖范围内。【推断】这个选择让试用成本接近零，也把增长绑在了浏览器这一个入口上。

### 可迁移的方法

1. 从每天都会遇到的小摩擦出发，写清现在要暂停几次、每次花多久。
2. 先做只走通主路径的版本，把范围压到十分钟能改完的程度，再决定要不要继续。
3. 选接口时先看是否支持全双工与说话人分离，这两项决定对话能不能插进去。
4. 准备一组「不该回答」的测试句，包括环境指令、附和与自言自语，逐条验证模型会不会抢话。
5. 把成本按分钟算一遍，据此设免费额度与提醒阈值。
6. 换一种内容形态做压力测试，比如没有字幕的播客，看取帧与字幕依赖哪一环先失效。

## 17 司马光砸缸：VoHive 与低成本验证码设备

**身份**：司马光砸缸的即刻主页跳转后只有 App 下载入口，履历与所在城市本次没有读到（okjike.com）。他手里养着十几个手机号（官方汇总页记录），这次分享的是怎么用便宜硬件把这些号码的短信收拢到一处。

**分享对象**：两套低成本收验证码的硬件方案，一套用二手大疆 4G 模块加 VoHive 面板，一套用二三十元的 4G Cat.1 裸板。

**关键词**：验证码、4G 模块、eSIM、Webhook。

### 他讲了什么

**起点是号码太多。** 注册、登录、跨境服务都要手机号接验证码，十几个号码逐个换卡、找手机、等短信，日常维护成本很高（官方汇总页记录）。

**方案一用退役的图传模块。** 大疆第一代 4G 图传模块二手七八十元，本质是移远 EG25-G 芯片（官方汇总页记录）。仓库标题写的是在 Mac 上用 UTM 跑 Linux 虚拟机，把模块伪装成移远 Quectel EC25，再部署 VoHive（github.com）。官方记录的说法是发一条 AT 指令永久解锁。

**VoHive 负责统一管理。** 面板可以统一收发短信、管理 eSIM 与海外卡的 VoWiFi，还能一键切换给 Mac 当 4G 网卡；缺点是必须常连电脑（官方汇总页记录）。页面返回的是名为 VoHive 2 的单页应用外壳，设备列表与具体功能本次没能核验（cool-glitter-88a5.iniwex.workers.dev）。

**方案二是一块裸板。** 度云物联的 4G Cat.1 USB 短信转发模块只卖二三十元，没有电池，不怕鼓包；烧录带飞书与钉钉 Webhook 的 Lua 固件后，插在 USB 扩展坞上通电就能跑，脱离电脑与 Wi-Fi，走卡自带的流量转发验证码，转发完自动删空短信（官方汇总页记录）。语雀上的产品页需要登录或由脚本渲染，本次只读到页面标题与一句平台简介，型号与售价没有核验（yuque.com）。

**防运营商风控靠定时断电。** 长期不动的静默模块容易被国内运营商判定为异常，他写了个程序定时给 USB 口断电重启，模拟手动插拔，这套做法已经稳定跑了两三年（官方汇总页记录）。

### 关键点分析

**第一，便宜的原因是型号退役。** 七八十元能买到 4G 模块，是因为第一代图传模块已经退市，芯片仍是标准的 EG25-G（官方汇总页记录）。二手硬件的性价比建立在「芯片通用、固件被锁住」这对矛盾上：硬件本身没坏，卡住的是厂商写的固件。判断一台旧模块值不值，先看它的芯片有没有公开的驱动与解锁资料。

**第二，解锁动作集中在一处，风险也集中在一处。** 仓库标题说要把模块伪装成 EC25（github.com），官方记录说是发一条 AT 指令永久解锁。把 USB 身份改成通用模组，系统才会按标准调制解调器识别它。【推断】改写模块身份可能触及厂商条款与保修，动手前要自己判断。这类改写一旦出问题，模块可能连原来的功能也回不去。

**第三，两套方案对应两种使用场景。** 方案一依赖 Mac 与 UTM 虚拟机，功能全，能管 eSIM 与 VoWiFi；方案二插电即跑，便宜、独立，只会转发短信。要管海外卡与 eSIM，前一套省不了；只想收国内验证码，后一套够用。两套都买回来，会发现它们分工不同：一套管入口，一套管兜底。两套的思路可以合起来用。

**第四，自动删短信同时解决容量与隐私。** 短信占模块的存储，写满之后新短信进不来，验证码就断了；转发完删空，验证码也不会长期留在设备里（官方汇总页记录）。这一步是长期运行的前提。转发失败要有重试，否则删空之后原短信就找不回来。容量与隐私一起处理，长期运行才稳。

**第五，风控针对的是行为特征，脚本把偶发维护变成固定节奏。** 长期静默的物联网卡会被运营商盯上，定时断电重启模拟的是人手动插拔的动作（官方汇总页记录）。两三年稳定说明这个节奏够用，也说明风控的判定并不严格。静默的判定标准由运营商定，用户看不到，只能靠经验试出可用的间隔。

**第六，Webhook 把硬件事件接进日常工具链。** 短信一进来就转发到飞书或钉钉群，谁都能看见，也留下了记录。代价是验证码会出现在群里，群成员与机器人权限都要收紧，重要账号的验证码不该走这条路。群机器人最好只在一个专门的小群里跑，成员名单定期清理。

### 可迁移的方法

1. 先列出每个号码绑定了哪些服务，标出还在用的，再决定要养几个号。
2. 购买二手模块前先确认芯片型号与公开的解锁步骤，不要只看价格。
3. 接入后先用串口工具发几条 AT 指令确认能通，再做解锁与部署。
4. 给转发加关键词过滤，只把含验证码的短信发送给 Webhook，其余留在设备里。
5. 写一个定时断电脚本，按天或按周重启 USB 口，并记录每次重启前后的收码情况。
6. 把号码、绑定的服务、续费日期记在一张表里，定期清理不再使用的绑定。

即刻主页跳转后只给下载入口，履历未能核验（okjike.com）；VoHive 面板只返回应用外壳，功能未能核验（workers.dev）；度云物联的语雀页面需要登录或由脚本渲染，产品参数未能核验（yuque.com）。

仓库的 README 正文本次没有读到，页面返回的 HTML 在导航部分就截断了，构建步骤、许可证与支持的模块批次都未核实（github.com）。七八十元与二三十元是分享时的行情，二手价格会随货源变化。

## 18 Chris Pang：GTIG 报告与海外 Agent 横评

### 关键点分析

**第一，补丁本身就是说明书。** 一份补丁的差异里写清了改哪个函数、缺什么检查，读它比读整份代码省力得多。报道说攻击者只需研究有限的材料：两个版本的源码、发行说明与相关的 PoC（thehackernews.com）。这让「披露即被利用」从例外变成常态。补丁越规范，差异越好读，逆向成本越低。

**第二，多智能体框架降低门槛的方式是分工固定。** ARTEX 这类项目把侦察、利用、后渗透写成角色，使用者给一个目标就能跑（thehackernews.com）。报道的表述是把入侵中的离散阶段与具体任务自动化。分工固定之后，能力就不再依赖使用者本人的水平。框架的名字会换，角色分工相对稳定。

**第三，LLMjacking 的账单异常往往先于告警。** 凭据被偷走之后，攻击方按 token 消耗你的额度，再把访问权折价卖出（thehackernews.com）。被盗方看到的第一个信号常常是账单曲线，却不容易看到入侵告警。给云资源设用量阈值，比事后排查更早生效。额度与凭据分开管理，损失就限于一家供应商。

**第四，五款产品的差异在入口与信任边界。** Today 做晨间简报，Hark 做单线程对话加 Panels，Poke 以短信为入口（poke.com 首屏写 right in your texts），Instinct 干脆没有界面，Muse 给每人一台云电脑（官方汇总页记录）。入口越轻，用户越愿意天天用；权限越重，范围越大。选型时先看这个入口要什么权限，再谈功能。入口不同，权限清单也不同。

**第五，Muse 把「助手是谁」与「助手知道什么」分开了。** 历史 Memory 记录事实，Soul 是人设的 Markdown 文件（官方汇总页记录）。改人设不必动历史，换模型也不必重写记忆。这是产品层面的一个结构选择，比功能列表更值得比较。两个东西分开之后，改一处不会连带另一处。边界清楚，调整时不会误伤另一处。

**第六，把出口固定在同一台云端机器上，是防地区检测的常见做法。** 浏览器与网络在同一台机器上，IP 与指纹才一致（官方汇总页记录）。Yorkson 的提醒说明这条不总成立，云服务商的出口路由自己会变（官方汇总页记录）。用这条之前，先确认目标服务是否允许这类登录方式。

**第七，报告与横评讲的是同一件事：授权。** Agent 能替你订餐、买东西、发邮件，也能被用来扫补丁、卖额度。区别在于谁握着授权、谁在看审计记录。分享者把安全报告放在横评前面，等于先讲风险，再讲产品。风险先讲清楚，推荐才站得住；顺序换了，听众的接受度就不同。

### 可迁移的方法

1. 读安全报告先记下它点名的框架与案例，再去搜对应的仓库与补丁编号。
2. 给 Agent 的每个动作分级：只读、可撤销、需批准、不可代做，按级配权限。
3. 把长期记忆与人设分成两个文件，改人设时不动记忆。
4. 试一款个人助理，先看它有没有审计记录与操作前确认，再看功能够不够。
5. 给云资源的用量设告警阈值，账单的异常峰值通常比其他信号来得早。
6. 需要固定出口时，把浏览器与网络放在同一台云端机器上，登录前先确认出口 IP。

### 边界与提醒

Chris Pang 的 LinkedIn 主页返回 999，履历未能核验（linkedin.com）。报告原文本次没有读到，只读到 The Hacker News 的二手报道；官方汇总页写「11 月安全报告」，报道页标注的发布时间是 11 月 16 日（thehackernews.com）。

五款产品的官网文案可以读到，价格、所用模型与地区可用性没有逐一核验。Hark 使用 Anthropic 模型、Poke 在 7 月被 Cognition 收购，这两条只有官方记录。「综合体验最好的是 Muse」是分享者的个人判断，本文按记录转述。

防封号的做法涉及平台的服务条款，账号风险由使用者承担。本节不提供规避检测的操作步骤。

## 19 Ricky Lin：《当观光客变成流浪者》

**身份**：Ricky Lin 的 LinkedIn 主页返回 999，履历没能读到（linkedin.com）。他这次带来一份自己做讲稿的演讲，用 Slidev 加 GPT-5.2 写成，题目是《当观光客变成流浪者》（官方汇总页记录）。

**分享对象**：一份从齐格蒙特·鲍曼《工作、消费主义和新穷人》出发，讨论 AI 替代与就业焦虑的讲稿，另附 3 分钟在线版与完整版 PDF。

**关键词**：观光客、流浪者、工作伦理、消费美学。

### 他讲了什么

**开场是一面标语墙。** 讲稿首屏铺满 12 条 AI 取代人类的行业标语，其中剪映小云雀 1.0 的「一句话打造一个爆款」正是他当年写的（官方汇总页记录）。把自己写过的文案放进被质疑的清单，这个动作定了整场分享的基调。

**重读鲍曼。** 他把全球化时期的产业外移与今天的 AI 替代放在一起对照：当系统不再需要本地劳动力，社会从工作伦理滑向消费美学，人群分成有选择权的「观光客」与「流浪者」（官方汇总页记录）。工作不再是身份的来源，消费能力接过了衡量人的尺子。

**他反对的归因方式。** 今天流行的「不学 AI 就会被淘汰」，在他看来仍是把结构性问题归咎于个人（官方汇总页记录）。产业外移与自动化带来的失业，被说成个人技能不够，责任从组织转到了个人身上。

**他给的出路。** 摆脱焦虑的办法是借创业与产品设计参与重塑价值分配（官方汇总页记录）。这是一条行动主张，讲稿里没有给出可验证的路径与案例。

**讲稿本身的做法。** 用 Slidev 写稿，配 GPT-5.2（官方汇总页记录）。Slidev 的稿子是 Markdown，改版、对比、上线都走文本流程。3 分钟在线版放在 Vercel 上，页面标题是「当观光客变成流浪者（3 分钟版）」（bauman-ai-3min.vercel.app）；完整版是 PDF（media.jant.me）。

### 关键点分析

**第一，标语墙是自证材料。** 12 条标语里有一条出自他自己（官方汇总页记录）。这类话术的生产者与承受者常常是同一批人：写文案的人也在被文案描述的那个行业里工作。把这层关系摆到台面上，批评才有分量。标语贴满一屏，观众先感到压迫，再听解释。

**第二，观光客与流浪者的分别在于能不能离开。** 按常见的解读，鲍曼用这两个词描述消费社会里的两种移动能力：观光客想去哪就去哪，流浪客走到哪都被当地规则拦住，移动能力背后是资源与证件。【推断】放到 AI 语境，有选择权的人把工具当加速器，没有选择权的人被工具重新定价。

**第三，工作伦理退场之后，消费美学接手。** 社会不再用「你有没有在工作」评价人，改用「你消费得起什么」（官方汇总页的转述）。这条线索能解释一个常见现象：裁员消息与消费广告可以在同一个信息流里并列出现，彼此不冲突。它也能解释，为什么商场广告比招工启事更显眼。

**第四，「不学 AI 就被淘汰」把责任放错了位置。** 技能论假设岗位还在，只是需要新技能；结构论看到的是岗位本身在减少（官方汇总页记录的观点）。两种解释对应两种应对：前者催人报课，后者催人改规则。把失业说成学习问题，等于让被裁的人自己承担解释成本。

**第五，参与重塑价值分配，是一条主张，并不构成方案。** 创业与产品设计确实能改变收益怎么分（官方汇总页记录），但它要求资源、时间与承担失败的余地，多数人没有这些条件。讲稿在这里停住，读者要自己补完。讲稿把这句结论放在结尾，听众带走的是态度，具体步骤要自己补。

**第六，用 AI 写一份批评 AI 叙事的讲稿，这种并置本身就是论据。** 工具可以用，解释权要争（官方汇总页记录）。他没有拒绝工具，也没有把工具当成中性物，这个态度比结论更值得带走。这份讲稿本身就是一次示范：用工具来做批评工具的事。批评与制作可以同时进行。

### 可迁移的方法

1. 把自己行业里的「AI 标语」抄下来，标出哪些是自己写过的、哪些正在被同事转发。
2. 读一本旧书时，把书里的结构与当下事件逐条对照，分别记下能对上的与对不上的。
3. 给同一份讲稿准备 3 分钟与完整两个版本，短版只留一条主线。
4. 用文本即代码的工具写稿，版本差异可以直接对比。
5. 讨论结构性问题时，把「个人能做什么」与「制度该改什么」分成两栏写，避免混为一谈。
6. 把讲稿放在公开链接上，让不同意的人能读到原文再反驳。

### 边界与提醒

讲稿页面只返回标题，正文由脚本渲染，幻灯片内容未能核验（vercel.app）；完整版 PDF 的类型是 application/pdf，本次使用的抓取工具不支持这种类型，文件没有读到（media.jant.me）。

12 条标语的原文、剪映小云雀 1.0 的版本信息、GPT-5.2 的使用方式，都来自官方汇总页的记录，本次没有读到讲稿正文逐条核对。鲍曼的论述按官方记录转述写成，书里的原话与章节位置未核对。

「参与重塑价值分配」是价值主张，讲稿没有给出可验证的路径。把它当成结论之前，先看自己手上有没有对应的资源与时间。

## 20 Jeff：若饭与 Supernote

**身份**：Jeff 的分享没有个人主页，官方汇总页只给了两个产品链接：若饭与 Supernote（官方汇总页记录）。他把这两件东西当作日常用品在用，讲的是长期使用之后的体感与一笔账。

**分享对象**：一件程序员熟悉的代餐，和一台上海公司做的墨水屏手写本，外加一次自行改装笔杆的经验。

**关键词**：代餐、墨水屏、手写、模块化。

### 他讲了什么

**若饭是用来应急的。** 赶路、赶稿、错过饭点的时候，冲一杯或开一瓶就能顶一顿（官方汇总页记录）。官网把它写成「让吃饭多一个省心的选择」（ruffood.com）。近期的新配方像 Huel v3.1 一样，加多了膳食纤维与姜黄素，肠胃敏感的人喝了可能略有烧胃感（官方汇总页记录）。【推断】这类调整通常是为了营养表更好看，代价由第一次喝的人承担。

**官网的产品线。** 若饭官网写它 2015 年从程序员团队的高效饮食需求起步，现有液体版 V3.11（420mL）、粉末版 V2.15（1kg）、固体版 V1.15（49g）、青春版 V0.3 等形态，页面标注累计服务 40 万用户（ruffood.com）。运营主体写作杭州悠购网络科技有限公司与浙江若饭食品科技有限公司（ruffood.com）。

**Supernote 是一台手写本，他换了笔杆。** 它由上海雷塔科技出品（官方汇总页记录）。J.K. Rowling 今年也发文称赞过它（官方汇总页记录）。核心是 FeelWrite 弹性软膜配永不磨损的陶瓷笔芯，解决玻璃屏写字打滑的问题（官方汇总页记录）。他买了官方内胆，塞进凌美 LAMY 的笔壳里自行改装；原装笔杆的握感不合手，换壳比换机器便宜得多（官方汇总页记录）。

**价格与售后。** 产线迁往日本长野组装，叠加内存涨价，7.8 寸模块化新款 Nomad 现售约 3000 元（官方汇总页记录）。初代 A6 X 的外壳出现老化微裂纹后，创始团队主动给老用户发了直减千余元的半价换新券（官方汇总页记录）。

**官网首页只读到外壳。** supernote.com 是 Shopify 前台，商品与参数由脚本渲染，本次只读到站点标题「For Those Who Write, For Those Who Create」，具体规格与价格没能核验（supernote.com）。

### 关键点分析

**第一，代餐卖的是省掉的决策。** 赶路时不用挑餐厅、排队、等出餐，开盖就喝（官方汇总页记录）。这类产品的用户要的是时间与确定性，口味排在后面。判断它值不值，看它一周替你省下几次选择。办公室里常备一箱，比临时点外卖省时间，也少一次选择。备货量按一周的加班次数估。

**第二，配方升级会带来体感代价。** 膳食纤维与姜黄素加多（官方汇总页记录），肠道敏感的人第一次喝容易不适。配方表上的数字变好，体感不一定跟着变。换代餐要按小包装试，先喝三天，记录饱腹时长与肠胃反应，再决定要不要囤。胃口与耐受是两件事，都要试过才知道。

**第三，手写的手感由膜与笔尖共同决定。** 玻璃屏打滑，弹性软膜提供一点阻力；陶瓷笔尖不磨损，省掉换笔芯的麻烦（官方汇总页记录）。两者配套，手感才立得住。只换其中一样，写起来仍然别扭。玻璃屏缺的，是笔尖与玻璃之间那层恰到好处的摩擦。试写时要写小字，也要画长线。

**第四，改装笔壳是用户对握感的投票。** 官方内胆塞进 LAMY 笔壳（官方汇总页记录），说明原装笔杆的重量与直径不合他的习惯。厂商留出可替换结构，用户就会自己调。这类改装需求，往往比问卷更能说明下一代产品该改哪里。改装件的生意，往往就是这么长出来的。厂商不必猜，看用户换了什么就知道。

**第五，3000 元的定价有供应链解释。** 产线迁到日本长野组装、内存涨价（官方汇总页记录），成本确实上去了。模块化设计的用处是把屏幕、主板、电池分开换，坏一处不用换整机，长期摊下来更划算。买之前先算自己会用几年，再判断这个价格算不算贵。用得越久，摊到每年的成本越低。

**第六，售后政策是最有力的口碑材料。** 初代外壳老化出现微裂纹，团队主动发半价换新券，直减千余元（官方汇总页记录）。把一次质量事故处理成信任，比任何参数表都管用。硬件公司做长期生意，这一环决定老用户会不会再买第二台。老用户的口碑，比新品发布更能带来复购。

**第七，两件东西的共同点是减少摩擦。** 一个省掉吃饭的决策，一个省掉纸笔与平板之间的切换。工具选型的标准可以很简单：它替你省掉的动作，一周发生几次；发生的次数够多，价格才谈得上合理。次数多的动作，值得为它单独买一件工具。先换用得最多的那一个。

### 可迁移的方法

1. 买代餐先买最小包装，连喝三天，记录饱腹时长与肠胃反应，再决定囤多少。
2. 选墨水屏手写本时，带自己常用的笔去试写十分钟，重点试小字与长划线。
3. 买笔之前量一下常用笔杆的直径与重量，优先选能替换内胆的型号。
4. 买模块化设备前，先确认屏幕、电池、主板能不能单独购买。
5. 下单前问清易损件的保修范围：外壳、笔尖、电池各保多久。
6. 记录自己每天重复的小动作，按次数排序，先替换排名靠前的那几个。

### 边界与提醒

若饭官网给出 2015 年起步、40 万用户与各版本规格（ruffood.com），这些是厂商自述，营养成分表与第三方检测本次没有核对。代餐不能替代医嘱，肠胃敏感者与有基础病的人应先咨询医生。

Supernote 官网由脚本渲染，商品页与参数页没有读到（supernote.com）。约 3000 元、产线迁往日本长野、半价换新券、J.K. Rowling 的推荐，都只有官方汇总页的记录，本次没有找到可核对的公开页面。

官方记录写的是「约 3000 元」，没有注明币种与含税情况；海淘与国内渠道的实际成交价可能不同。这类价格信息变动快，购买前应以商品页为准。

**开场用了一个马拉松的比喻，随后给出核心判断。** 基普乔格马拉松破二时，身后跟着 41 位配速员（官方汇总页记录）。纪录写在一个人的名下，过程由一群人完成，这是他理解开源社区的方式。他由此提出「智能可以租，记忆必须自己拥有（Intelligence can be rented. Memory must be owned.）」（官方汇总页记录）：生成式 AI 让智能近乎免费，开源就不再只是软件工程师的事，任何可以形式化的经验与创作都能协作复用。

**他自己先试了一次。** 2024 年，他用早期的 Suno 与个人声音克隆，花 100 小时在 Spotify 发行了专辑《Dream Again》（官方汇总页记录）。Spotify 上的页面标题是「Dream Again - EP by 思为」（open.spotify.com）。做一张专辑要处理的环节，从写词、编曲到发行，正好是一份可以被形式化的经验清单。

**Nowledge Mem 管上下文。** 它是跨工具的上下文管理器，内置 Nowledge Bridge，让不同 AI 会话之间双向通信（官方汇总页记录）。官网首屏写「AI tools change. Your memory should compound.」，意思是 AI 工具会换、记忆应当不断累积，界面分 Timeline、Memories、Threads、Graph、Library、Skills、Context 等栏目，并写明覆盖 Claude、ChatGPT、Cursor（mem.nowledge.co）。

**HawDB 管存储。** 它是一个用 Rust 写的嵌入式多模上下文数据库（官方汇总页记录）。官网写当前版本 0.34.0，把图、SQL、全文与向量检索放进同一个进程、共享一份快照与提交边界，Cypher 与 PostgreSQL 方言的 SQL 共用一套优化器，BM25 与 DiskANN 检索是可重建的投影（hawdb.ai）。

**con 与 Ducter 分别管入口与调度。** con 基于 Ghostty 与 Zed 的 GPUI 构建，是开源的极客终端（官方汇总页记录），官网写它终端优先、GPU 加速、内置 Agent，面向 SSH、tmux 与 Agent 工作流（con.nowledge.co）。Ducter 是个人 Agent 中枢：Conductor 被 Meta 收购之后，他趁去日本出差的周末，宅在 Airbnb 里手搓了这个开源项目（官方汇总页记录）。它自托管调度已经订阅的 Claude Code、Codex、pi 与 DeepSeek Harness，支持操控手机模拟器，也能在海外直接打电话订餐厅；官网写它把任务交给这些已付费的 Agent，每个任务独立分支，合并由人确认，代码留在自己的机器或服务器上（ducter.ai）。

### 关键点分析

**第一，「租智能」对应按 token 付费的现状。** 模型能力可以随时换供应商，价格随竞争下降，调用按量计费。这条判断把注意力从模型转到数据：模型是租来的，用过就还；记忆留在自己手里，才有复利。把这两件事分开看，预算与注意力的分配就清楚了。模型按需换，记忆长期积累。

**第二，「拥有记忆」是可操作的要求，并不停在口号。** Nowledge Mem 把对话、决策与发现存在本地，跨 Claude、ChatGPT、Cursor 共用（mem.nowledge.co）。判断一款记忆工具，看三件事：存在哪、怎么导出、换模型之后还能不能用。这三个问题能筛掉大部分产品；只做导入、不做导出的工具，第二个问题就过不了。导出格式最好是纯文本，迁移成本最低。

**第三，Bridge 解决的是工具之间的隔断。** 不同 AI 会话之间双向通信（官方汇总页记录），前面 hwang 提的「最好用的 A2A 协议是电子邮件」是同一问题的另一种解法。两相比较，邮件胜在通用，Bridge 胜在结构化。隔断的实质是上下文没法带走，换个工具就得重讲一遍。协议选通用格式，迁移时才不费力。

**第四，HawDB 把四种数据形态放进一个进程。** 图、SQL、全文与向量共享一份快照与提交边界（hawdb.ai），省掉图库、关系库与索引之间的同步作业。对 Agent 来说，检索与事务在同一处发生，结果不会互相打架。代价是全放在一个进程里，隔离性要靠分支来做。单进程省事，也把可用性押在一处。

**第五，Agent 分支是给并行任务准备的隔离。** 每个 Agent 拿到写时复制的可写分支，改动留在分支里，宿主决定写回哪些结果，分支之间不自动合并（hawdb.ai）。这比让多个 Agent 同时改一份数据安全，代价是要有人做合并的决定。分支开得越细，写回时越好判断，也越容易回退单条改动。

**第六，Ducter 的位置是调度层。** 它不自建模型，把手头的 Claude Code、Codex、pi 与 DeepSeek Harness 排成队列（官方汇总页记录）。任务在自有机器上跑，花钱与对外发消息之前要人批准（ducter.ai）。这一层做得好不好，取决于它能不能在正确的时候把结果交给人，其余时候保持安静。它不产生新的账单，这一点对已经订阅多个服务的人很实际。

**第七，开源的比喻指向参与方式。** 41 位配速员（官方汇总页记录）说明纪录由一群人共同完成。智能便宜之后，能协作复用的经验范围扩大了，写提示词、整理评测集、记录流程，都算参与。写一份能被别人直接复用的清单，就是最小规模的开源。清单越具体，别人越容易接着用。

### 可迁移的方法

1. 把对话、决策与笔记存在自己能导出的地方，换工具之前先确认导出格式。
2. 选记忆工具时问三个问题：数据存在哪、怎么导出、换模型后还能不能用。
3. 把检索与事务放在同一个进程里，能省掉一类同步故障。
4. 给并行 Agent 各开一条分支，改动先留在分支，写回由人决定。
5. 把已付费的模型额度接进一个自托管调度器，任务队列与审批留在自己手里。
6. 参与开源时先找可以形式化的那部分经验：提示词、评测集、流程文档。

### 边界与提醒

讲稿页面只返回标题「Build things with magic」，正文由脚本渲染，幻灯片内容未能核验（siwei.io）。四个项目的官网文案可以读到，功能细节、许可证与收费方式没有逐项核验。Nowledge Mem 有 Cloud 与定价页，Mem Vault 以许可证形式售卖（mem.nowledge.co）；HawDB 的版本号 0.34.0 取自页面标注（hawdb.ai）。

「智能可以租，记忆必须自己拥有」是价值判断。它解释了这几个项目为什么这样设计，本身没有经过验证。自托管 Agent 中枢要长期开机、要维护依赖、要自己处理密钥，这些都是成本。

Ducter 自述免费开源（ducter.ai），实际可用性与稳定性要自己试。海外打电话订餐厅这类能力涉及当地电信规则与平台条款，使用前要自己确认。

## 判断一：上下文正在变成可以托管、复用与共享的资产

杨云童的 Handoff 把一句「对哪个项目有用」写进六节提示词骨架，ManuFold 按原书页码作答，KeyKeeper 让密钥不进模型上下文（第 02 章）；古思为在讲稿里提出智能可以租、记忆需要自己拥有，并给出 Nowledge Mem 这类工具（第 21 章）；火箭君CC 把资料存成 Markdown，用 AnyDoc 转换格式（第 10 章）；elioWang 让 Agent 在没装依赖的项目里静态解析路由（第 09 章）；Owen 的调研工具从真实上线流程里取样（第 11 章）。

这些做法的共同点，是把散在会话里的上下文变成文件、库与检索入口，换会话、换电脑都能接上。代价是维护：文件要整理，库要更新，提示词骨架要跟着项目变。

## 判断二：一次证伪比十次证明更省成本

Aria 把 MVP 的用途限定为收集信息，0 人使用也是一次证伪（第 04 章）；草原张讲的 TOI-7930 候选信号要经过 7 年 22 次凌日的核对（第 14 章）；Chris Pang 解读的 GTIG 报告说明攻击方在补丁发布后的窗口里批量验证（第 18 章）；yikai 用便宜模型在 5 到 15 元内试出一套接口的权限问题（第 03 章）。

成本下降之后，验证某个假设的代价低到可以反复试，关键变成先写清楚什么结果算否定，再决定投入多少。

## 判断三：门槛移到上架、被看见与被信任

hwang 的 AirBuild 把需求、设计、代码与上架串成一条链，连拒审反馈都交给 Agent 处理（第 12 章）；elioWang 的 MCP 工具解决 Agent 读不懂项目结构的问题（第 09 章）；Xinxia Ling 的 NX2Apple 要求 macOS 26.6 与 Xcode 27.2，首次切地图要编译着色器（第 15 章）；Lingo 的 WatchWithU 接口目前限时免费，后续商用按分钟计价（第 16 章）；陈雅娜收集 5 家互动设计工作室，给产品首页找参考（第 08 章）。

能做出来的人变多之后，能不能上架、被搜到、被信任，成了新的分界线。

## 判断四：设备与本地环境重新提供差异

海涛的 Pinky 让 MCP 客户端操控真机，银行与密码器默认对 AI 隐身（第 01 章）；Yorkson 的掌机谱系从百元 Linux 机到 Steam Deck（第 05 章）；张峻玮在 iPhone 里跑带桌面的 Linux 沙盒（第 06 章）；司马光砸缸用七八十元的 4G 模块收验证码（第 17 章）；Jeff 的 Supernote 与若饭（第 20 章）；火箭君CC 的本地优先（第 10 章）。

云端能力越来越接近，设备、网络与系统权限这些本地条件反而决定了能做什么。

## 判断五：智能可以租用，记忆与判断需要自己持有

古思为的讲稿把开源协作与个人记忆库放在一起（第 21 章）；杨云童把个人上下文写进本地 Markdown（第 02 章）；Aria 主张主业深耕、跨界领域学到 60 分（第 04 章）；Victoria Zhang 走访四地，看到硅谷、波士顿与纽约对 AI 的不同态度（第 13 章）；Ricky Lin 重读鲍曼，讲「观光客」与「流浪者」的分裂（第 19 章）。

模型可以按次购买，判断与记忆需要长期积累。同一套工具在不同人手里差距很大，原因多半在这里。
